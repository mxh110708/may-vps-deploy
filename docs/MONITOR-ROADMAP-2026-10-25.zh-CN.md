## 当前基线

上一公开基线为 Deploy v0.9.36、Server RC3、Agent／Web RC1。本轮发行集合为 Deploy v0.9.37、Server v0.1.0-rc.8、Agent v0.1.0-rc.4、Web v0.1.0-rc.4、May Status v2.2.2-may.17；监控组件继续明确标记为候选版。基础能力包括：

- M1：专用只读指标、实例绑定、Deploy 监测页、范围／有效期和失效保护。
- M2：独立 Server／Agent 的固定版本部署、升级、备份、恢复、启停和确认丢失核对。
- M3：独立 HTTPS 接入计划、SSH 与 HTTPS 安装身份比对、指定单节点凭据及连续上报验收。

服务端和 Web 已继承历史、探测任务、普通通知等功能。后续先核对其真实可用范围、补齐运维流程和验证，不把继承功能笼统写成尚未实现，也不以路由存在代表已经验收。

隔离验证和生产迁移分别记录。2026-10-26 用户明确要求直接正式迁移，取消分阶段试用：BERO 已接管现有入口，六台 May Agent 已核对连续上报，旧 Komari 按授权停用。真实公网 HTTPS 已核验；M5 长期资源分析与异常复核已完成，原始异常和证据限制不删除。后续操作前重新核对实际目标，历史归档不代替在线状态。实施与主题状态见 [M8／M9](MONITOR-M8-M9-2026-10-26.zh-CN.md)，日常维护见[操作手册](MONITOR-OPERATIONS.zh-CN.md)。

## M4：先补齐 Agent 与凭据维护

1. 增加独立的 Agent 配置维护动作，不借版本升级修改端点，也不为相同版本伪造升级。
2. 支持显式更换服务端 HTTPS 地址与 Agent Token，保留该 May 节点 UUID 和受管服务身份；目标身份发生变化时重新核对归属。
3. 首先使用维护者在 May 管理端准备的有效凭据。Deploy 不为此保存长期管理员 API Key，也不将只读令牌用于管理员操作。
4. 应用前验证新端点的 TLS、安装身份和节点凭据；应用后验证实际 Agent 连接与连续新上报，再提交并同步加密归档。
5. 补齐只读凭据的范围、到期、续期、撤销和过期提示，清楚展示需要重启所选服务才能生效的动作。
6. 回退核对原端点与原凭据是否仍有效。若旧 Token 已在服务端撤销，恢复旧文件不能算恢复成功，应保留“需要恢复”状态和重新配置入口。
7. 对错误 Token、错误主机名、不受信证书、错误节点／来源、取消、服务启动失败及回复不明分别测试。确认丢失时继续按事务身份核对，不重放变更。

本轮不同时增加监控协议、通知渠道或生产批量迁移。

## M5：稳定性、历史与低开销

- 验证服务端重启、网络中断、Agent 断线／重连及 WS／HTTP 交替；缺失、过期和离线分别显示，避免旧连接覆盖新状态。
- 核对指标时间、重启后的累计流量、计数回退及无效值。历史图中的空洞不能被填成真实的零值。
- 检查采样、发送队列、写入批次、连接和缓冲区上限，以及数据库保留、降采样、清理、备份大小和磁盘不足时的行为。
- 记录单节点和覆盖实际使用规模的多节点负载；分别测量 Agent、Server、Web、Deploy 的进程资源，主机内存指标不能代替进程开销。
- 观测空闲、持续上报、查看图表、Deploy 隐藏／关闭和断网情形。内存优先、CPU 次之，同时保留数据新鲜度与响应能力。
- 先建立基线，再决定默认采样和历史保留参数；至少完成 24 小时隔离观测。只保留有资源、稳定性或可用性收益的改动，记录代价与验证边界。

持续采集、历史和告警由 Server／Agent 承担，Deploy 关闭后仍应正常运行；不让桌面工具长期持有 SSH 会话或高频轮询来代替监控服务。

## M6：线路探测与告警闭环

- 先核对继承的探测和通知实现，补行为测试和缺失流程；通知先完成一个实际使用渠道的验收，再按需要扩展其他渠道。
- 本次线路对照沿用此前记录中的广东使用基线，优先广东三网；实际探测目标、协议、端口和可达性在上线前重新核对，不把旧目标当作当前事实，也不将广东写死为产品唯一地域。
- ICMP、TCP 建连和 HTTP 应用探测分别配置与展示。VPS 到目标的结果须注明方向，不能称为用户到代理入口或完整代理业务的延迟。
- 仅对明确选定的目标做有界探测，限制频率、超时和并发；缺少 ICMP 权限时显示受限，保留独立 TCP／HTTP 检查。
- 离线、持续高延迟／丢包、资源或磁盘异常采用连续确认、恢复条件、去重、通知冷却和维护静默；阈值按地区与探测类型设计，再允许按组／节点调整。
- 通知发送失败、重试上限和恢复通知应可核对；自动化使用本地接收器，真实外发在用户选定并授权渠道后执行。
- 监控服务自身失联须能由独立存活检查发现，不能只依赖故障服务给自己发告警。

May Monitor 提供监测和告警。Route 的自动故障切换仍由 Route 管理，两者不相互替代或因本轮自动联动修改路由。

## M7：完善日常界面

- 在现有 Web 基础上完善 May 可见标识及简中／英文关键流程，保留上游版权和必要内部协议标识。
- 完善概览、节点详情、历史图表、线路结果和告警状态，明确在线、离线、无样本、过期、鉴权失败和监控服务不可达。
- Deploy 提供受管实例摘要、凭据／接入维护及核验结果，完整历史和管理可进入 May Web；避免在桌面复制全部管理功能并扩大凭据权限。
- 只读权限不足、令牌到期、TLS 错误和服务身份不匹配分别给出可操作提示，初次尚未完成采集时不提示已经故障。
- 可见页面按需要刷新，切走、隐藏和关闭时处理连接／请求；保持后台采集独立运行，并实测浏览器和桌面资源。
- 公共视图与私人指标的范围单独验收；保持 API 不被公共缓存，凭据不进入 URL、截图或普通日志。

## M8：生产直接接管（用户于 2026-10-26 修订）

1. 重新盘点实例和 Komari 实际位置、节点身份、探测、告警、历史及备份；五台旧节点加重装后新增的 AetherCloud，共六台。
2. 用户明确选择直接正式迁移。BERO 接管现有 HTTPS 入口，Tunnel／CF 不修改；不是独立域名或 72 小时并行试用。
3. 新建独立管理员、节点 Token 和只读授权，按旧 Token 与 Client UUID 核对映射；不复制旧会话或整个认证数据库。
4. 一致性备份后仅切换所选监控组件，检查每台真实连接、连续推进报告、公网 HTTPS 与安装身份。生产业务、SSH、Tunnel、Docker 和独立 M5 单元保持。
5. 验收后提交退役旧监控并取消该切换回退计时器；旧程序／数据及已下载校验的备份保留，不能被过时自动跟进擅自恢复。
6. 计划、状态及 DPAPI 新凭据同步到 Deploy 私人归档。旧历史未导入，按备份保留；不开放通用数据库导入或 SQL 控制台。M8 的直接接管不代替 M5 长测、真实外发或独立主机存活检查验收。

真实公网 HTTPS、Cloudflare／反向代理、通知外发、业务机资源和退回结果分别留证；生产并行期的额外开销也需记录。

## M9：正式版与交接

- 固定 Server、Agent、Web 和 Deploy 的兼容矩阵，版本号可以不同；源码、前端提交、构建依赖、附件和摘要必须对应。
- 对最终范围执行鉴权、撤销、隔离、更新完整性、恢复和故障回归；依赖公告结合实际导入／调用路径复核，保留未覆盖及未修复记录。
- 达标后再确定监控正式版版本，不能因轮次完成就直接去掉预发布标记。桌面安装更新仍由用户操作。
- 把部署、升级、凭据轮换、只读授权、历史保留、告警、备份恢复、迁移与退役整理成可独立执行的手册。
- 检查并移除已经失去作用的临时迁移代码与旧候选入口；仍有明确使用者的兼容路径单独说明，不能靠隐藏失败维持表面兼容。
- 上游更新继续手动选定提交、审查差异、测试和按需合入，不自动同步开发分支或启用 Agent 自动升级。

本阶段正式支持以当前 Windows 控制端和 Debian 12／13 amd64 运维范围为准；仅交叉编译的其他架构／平台不自动升级为已实测支持。

## 本阶段完成的定义

监控支线首阶段完成，指 May Monitor 能在用户选定的实例范围内独立承担日常指标、历史、线路探测、告警和维护，Deploy 的管理流程完整，选定生产迁移及退回验收完成，并具备可复核的正式发行与手册。

远程终端、任意命令、文件管理、SQL 控制台、插件／脚本扩展、旧数据库整体导入、真实 SSO 和新增平台支持，不作为本阶段必须开启的能力；仍按独立需求审查。安全维护与上游适配是后续持续工作，不宣称永久完成。

每轮交付必须包含：功能变更、准确源码和配套版本、正常／失败／取消／恢复的验证、资源影响、遗留边界与是否发布。计划变更同步本文件，防止再次出现轮次和实际内容不一致。
