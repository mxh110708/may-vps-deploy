# 第八轮：独立 TCP 端口转发

本轮为受管 Debian 12／13 实例增加独立转发组件。每条规则在实例上监听一个 TCP 端口，按来源白名单接收连接，再连接一个明确的 IPv4 或 IPv6 目标。它独立于现有代理协议入站，不要求重新安装 Xray、sing-box 或监控服务。

源码及下列本地检查已完成，后续随 v0.9.35 整合发行；未安装或应用到生产 VPS。本文保留第八轮的验证边界，整合结果见[发行验证](TESTING-0.9.35.zh-CN.md)。

## 使用流程

1. 在实例详情中选择「管理转发」，打开「独立 TCP 端口转发」。实例须已完成部署／接入，且没有待恢复事务。
2. 选择「保存转发规则」，点击「添加 TCP 转发」。已有规则会按竖排卡片回填，可编辑、停用或移除单条规则。
3. 填写名称、监听地址族及端口、目标 IP 及端口、允许来源和验收方式。只编辑表单不会连接服务器。
4. 点击「审阅」，核对每条规则的目标、来源范围、启用状态及影响，再从统一任务审阅提交。
5. 任务核对服务器、管理 SSH、组件归属和实际端口占用，保存恢复点后应用。启用的规则全部通过所选应用验收，并再次核对配置及管理通道后才提交。
6. 后续选择「只读检查已保存转发」，复核实际配置和经转发的应用连接；选择「移除全部受管 TCP 转发」则移除本组件及其白名单，并同步受管防火墙端口。

点击返回或取消审阅不创建远端任务。无效输入保留在原表单中，便于修正。只读检查不应用未保存的编辑，也不创建远端快照；它会更新本地检查结果。

## 字段与能力边界

| 字段 | 规则 |
| --- | --- |
| 规则数量 | 每台实例最多 16 条，稳定规则 ID 不作为显示名称 |
| 名称 | 1–80 个可打印字符 |
| 监听 | IPv4、IPv6 或双栈；监听相应地址族的所有接口 |
| 监听端口 | 1–65535；每条规则使用独立端口，包括已停用的规则 |
| 目标 | 单个明确的单播 IPv4／IPv6 地址及端口；本轮不支持域名目标 |
| 允许来源 | 每条规则 1–32 个 IP 或 CIDR；逐行填写，也可用逗号分隔 |
| 验收 | TLS 握手和证书、SSH 2.0 协议响应，或已保存代理节点的实际出口探测 |

CIDR 会规范化为网段地址。双栈验收逐个连接已归档的实例 IPv4 和 IPv6，因此两种地址都必须有效，而且控制电脑使用的两种公网来源都须被允许。系统回环接口用于本机服务，不受外部来源限制。

明确填写整个地址族的 `/0` 网段表示允许该地址族的所有来源；没有自动追加全网来源的默认值。目标服务器看到的是转发实例的源地址，目标侧已有的防火墙或可信入口限制须允许该实例。本轮不会自动修改目标服务器的访问控制。

这是一项 TCP 字节转发功能，不支持 UDP、PROXY protocol、隧道封装、流量配额或跨实例多跳编排。它不改写客户端方案、节点角色或已导出的链接；需要使用新监听地址的客户端由用户另行配置。

## 应用验收的含义

验收从运行 Deploy 的控制电脑连接转发实例的监听端口，不从转发服务器直接连接目标来代替外部可达性检查。服务商安全组、控制电脑到 VPS 的路径以及来源白名单都会实际参与验收。

| 方式 | 检查内容 | 不代表什么 |
| --- | --- | --- |
| TLS | 经转发完成 TLS 握手，并按填写的 TLS 域名验证主机名和证书链 | 不登录应用，不证明全部 HTTP 页面或其他业务行为正常 |
| SSH | 经转发收到完整 SSH 2.0 协议响应 | 不登录，不验证服务器主机公钥，不替代正常 SSH 身份确认 |
| 已保存代理 | 临时复制选定节点，保留鉴权及 TLS 参数，只将连接端点改为当前转发监听，使用已有 sing-box 诊断执行出口请求 | 不修改原节点，不绕过来源校验，不证明所有业务网站可用 |

代理验收只支持现有诊断器能够完整表达的原生节点。选择来源会带入目标地址、端口和节点指纹；提交前及执行时重新核对。节点被移除、凭据或连接发生变化、与目标不一致，均需重新选择和审阅。转发配置只保存来源引用和指纹，不复制鉴权明文。

正式应用使用系统信任库验证 TLS，没有关闭证书校验的界面选项。测试 CA 仅供独立本地夹具使用，不安装到 Windows 信任库。单项 TLS／SSH 验收有 12 秒时限，代理验收有 75 秒时限，整体最多 3 分钟，均支持取消；任一启用规则未完成验收就不能提交。

停用的规则仍保存参数和端口保留关系，不监听、不产生应用探测。全部规则停用时，检查只证明已停用状态和组件一致性，不产生“转发可达”的结论。

## 转发引擎与资源

复用 Debian 自带的 `systemd-socket-proxyd`，不下载第三方转发二进制，不新增常驻控制面或 Agent。systemd 保留监听套接字，有连接时按需启动工作进程，每条规则最多 256 条并发连接。

工作进程在**没有连接持续 60 秒**后退出；监听继续存在，后续连接可重新激活。该时间不是连接空闲超时，不会仅因一条已建立连接暂时没有数据就主动断开它。这里描述的是进程生命周期设计，不是内存或吞吐基准测试结果。

工作进程使用独立动态用户、空能力集、禁止提权、只读系统目录及受限地址族。系统须已有 Python 3、nftables 和 systemd 转发程序；预检缺失时停止，不在后台安装依赖。现有 Debian 部署流程会准备基础系统组件。

## 端口与防火墙

提交前同时核对私人归档中的管理端口、已安装协议／监控端口和远端真实监听。目标指向本组件本地监听、规则端口重复或未知进程占用端口时停止。IPv6 监听明确使用 IPv6-only，双栈使用两套监听，避免隐式占用另一个地址族。

本组件拥有独立的 `inet may_tcp_forward` nftables 表，对启用规则先允许指定来源，再拒绝该监听端口的其他外部来源：

- 实例由 Deploy 管理防火墙时，同步主受管防火墙的 TCP 端口放行；独立来源白名单仍然生效。
- 实例选择保留既有防火墙时，不修改它；所需端口须事先允许，既有更严格规则仍可能阻断连接。
- 不更改服务商安全组，不清空其他 nftables 表。

保存编辑会重建当前转发组件的监听，当前转发连接会中断。审阅中明确显示这一影响；普通检查不重建监听。现有代理入站、SSH 和监控不在该操作的服务变更范围内。

## 归属、失败与恢复

远端资源限定为本组件配置目录、专用 systemd 单元及独立 nftables 表。私人计划保存规范化规则，私人状态保存远端资源摘要和逐条验收结果。资源摘要包含已归档文件、运行白名单及套接字启用状态；不以按需工作进程暂时退出判断故障。

预检拒绝未知同名资源、符号链接、额外文件、单元覆盖或外部改写。审阅后归档／方案发生变化会使任务失效；服务器实际摘要不同也会在写入前停止，不接管外部配置。

应用前使用现有事务锁、组件范围备份和定时回退保护。备份固定本轮恢复程序及校验摘要，避免日后应用升级改变旧事务恢复逻辑：

1. 应用失败、取消或验收未通过，恢复本次转发及本次涉及的受管防火墙。
2. 写入或提交的回复丢失，进入既有对账与恢复流程，不盲目重放应用命令。
3. 恢复只接受原快照或本次审阅的文件内容；未知外部编辑保留并报告需要人工处理。
4. 恢复开始前记录意图；若恢复本身在删除本次文件、还原原文件之间中断，下次可以继续恢复。仍然拒绝出现的未知内容。
5. 完成后复核原文件、白名单和套接字启用状态。恢复新安装则须确认本组件完整消失。

实例健康检查也会只读核对配置、监听和白名单是否匹配归档，将异常列为告警，不在健康检查中自动修复或重复应用探测。退役实例前须先单独移除 TCP 转发，避免卸载其他组件后遗留监听。

第八轮初测时，Windows 的 `VirtualMachinePlatform` 禁用、`vmcompute` 缺失，因此当时跳过 Linux 测试。用户启用功能并重启后，第九轮已通过 WSL Ubuntu 补测；未修改 WSL 网络或系统代理来运行测试。

补测发现 systemd v255 的 `socket-proxyd` 按最后一个冒号分割目标，不移除 IPv6 的方括号。原先的 `[IPv6]:端口` 工作进程参数导致解析失败，现已改为该程序接受的 `IPv6:端口`；`ListenStream` 继续使用规定的方括号格式。依据为 [systemd v255 实现的 resolve_remote](https://github.com/systemd/systemd/blob/v255/src/socket-proxy/socket-proxyd.c)，最终两种地址族均已实际转发通过。

Windows 回环使用独立中继与合成 TLS／SSH 服务，验证控制端适配器，不能充当 Debian 的 systemd／nft 全生命周期验证。Linux 两项真实引擎测试只覆盖实际工作进程，不等于完整主机安装／重启／回退或生产公网已通过。尚未连接生产 VPS，本轮没有 WAN 性能数据。
