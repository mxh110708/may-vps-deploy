# 第十六轮：TUIC v5 独立入站

本轮将 TUIC v5 接入已有通用入站、用户、证书、出站、来源和事务模型。代码与隔离验收独立于实际 VPS，当前发行基线仍为 v0.9.38；第十五、十六轮均尚未打包、推送或发布。本文适用于包含本轮源码的构建，不表示已安装版本已具备这些功能。

## 功能范围

| 项目 | 本轮行为 |
| --- | --- |
| 服务器 | 复用固定 sing-box，每个 TUIC 入站使用独立 UDP 监听、服务身份和配置。 |
| 用户 | UUID 与密码分开管理，多用户、共享引用、密码／UUID 轮换；秘密随原私人归档加密保存。 |
| TLS | 独立证书引用、SNI 覆盖及有效期检查，TLS 1.3，固定 `h3` ALPN；不关闭证书校验。 |
| 拥塞控制 | cubic、new_reno、bbr，默认 cubic。指 QUIC 拥塞控制，与 Linux TCP BBR 内核选择分别管理。 |
| 应用 UDP | native 数据报、quic 可靠流；两种方式均须返回实际代理 UDP 业务响应。 |
| 客户端 | 从已验收入站逐用户／地址族生成 Mihomo、sing-box 原生节点和完整配置。 |
| 维护 | 检查、启停、换证、轮换、移除、包内固定核心更新；失败按受影响入站及自有防火墙恢复。 |

第十六轮新增 TUIC v5，不接入 TUIC v4 Token，不启用 0-RTT，不增加额外常驻代理层。不将 TUIC 放进仅承载 TCP 的透明转发；服务器下一跳的后续扩展见[第十七轮](SERVER-QUIC-ROUND-17-2026-10-28.zh-CN.md)。`tuic://` 链接导入／分享不是本轮范围，使用完整客户端配置，不能把“原生节点可导出”误作分享链接已支持。

## 使用步骤

1. 在受管实例进入「通用多入站 → 管理入站」，新建 **TUIC v5 / QUIC**。新建入站会建立独立用户 UUID 和随机密码。
2. 填写监听地址和 UDP 端口，选择用户、证书与出站。证书需覆盖 SNI，且具有匹配私钥和足够有效期。服务商安全组须放行该 UDP 端口；TCP 同端口是否可连接与此验收无关。
3. 按需要设置拥塞控制、UDP 中继、心跳与鉴权等待。默认即可用于首次验收，后续再按实际线路调整。
4. 用户页分别编辑 UUID 与密码；生成新 UUID 和生成新密码是独立操作。共享用户被修改时，审阅列出全部引用入站，不能只更新其中一个客户端文件。
5. 审阅协议、端口、SNI、用户引用、证书、出站、0-RTT 关闭状态及受影响入站后执行。
6. 等待每个用户和导出地址族通过真实 TUIC／HTTPS 与应用 UDP 回程。失败时先看具体阶段，不以服务进程存在或 TCP 通为替代依据。
7. 在配置设计选已验收来源，生成并校验 Mihomo／sing-box 候选，再明确导出。节点保存、文件导出和客户端已加载是不同状态。

### 参数与两端对应

| 字段 | 默认与范围 | 对应关系 |
| --- | --- | --- |
| 用户 UUID | 自动生成，有效且非全零的标准 UUID | 与密码作为一对写入服务端和客户端；同一入站拒绝重复 UUID。 |
| 用户密码 | 自动随机生成，16–256 个可打印字符 | 与 UUID 独立，不能把密码当作 UUID 或旧版 Token。 |
| SNI／证书 | 显式选择 | 证书必须覆盖所填域名，两客户端保持相同身份和证书验证。 |
| CongestionControl | cubic；可选 new_reno、bbr | sing-box 的 `congestion_control`、Mihomo 的 `congestion-controller`。 |
| UdpRelayMode | native；可选 quic | sing-box 的 `udp_relay_mode`、Mihomo 的 `udp-relay-mode`；不额外叠加 UDP over stream 扩展。 |
| HeartbeatSeconds | 10，整数 5–120 秒 | sing-box 以 `Ns` 表示；Mihomo `heartbeat-interval` 换算为毫秒。 |
| AuthTimeoutSeconds | 3，整数 1–30 秒 | 服务器等待协议鉴权的上限；并非客户端下载超时。 |
| 0-RTT | 固定关闭 | sing-box `zero_rtt_handshake=false`；Mihomo `reduce-rtt=false`、`fast-open=false`。 |

监听端口参加现有管理、固定角色、通用入站、跳跃集合及转发端口的冲突检查。TUIC 只需要该监听的 UDP，主机防火墙不会为它多开 TCP。远端就绪检查核对同一服务 PID 的 UDP 监听，其他进程或 TCP 监听不能代替。

## 验收与恢复设计

TUIC 的 HTTPS 请求由隔离客户端的真实 `tuic` outbound 执行；不先用 TCP 探测 UDP 监听，不添加直连或其他协议回退。随后在同一个隔离客户端使用 SOCKS UDP 通道发送 DNS 请求，控制端只把数据报送到自己的回环中继，不直接查询外部 DNS。检查中继身份、目标地址／端口、分片字段、随机 DNS ID、原始问题和匹配回答；UDP 失败即使 HTTPS 成功，也不能提交或生成已验收来源。

正常验收按出口地址族使用 Cloudflare 公共 DNS（IPv4 `1.1.1.1` 或 IPv6 `2606:4700:4700::1111`）查询保留示例域名 `example.com`，与原有协议验收采用相同思路。该步骤检验 UDP 回程，不能证明任意 UDP 应用、大包、吞吐或所有 DNS 都可用。若代理出口不允许访问此 UDP DNS，应先明确网络限制并保留失败结果，不能改为直连查询后冒充通过。

每个用户和地址族的结果与当前连接摘要绑定。改 UUID、密码、证书、出站、核心或协议选项后，旧来源失效；停用入站不可导出为当前可用来源。检查和变更验收都是有限任务，不新增后台轮询或常驻验收进程。

保存沿用「预检 → 范围快照 → 应用 → 协议／业务验收 → 提交」。失败或取消恢复受影响入站与本次自有防火墙；无关服务保持原运行身份。失去提交响应先核对原事务，不自动重放。核心更新会明确列出所有共享该固定 sing-box 的入站，失败恢复原版本；不会连带更新固定 Xray。

移除入站只移除其配置／服务。用户、证书、出站有共享引用时不能级联删除；私人归档和未完成事务不能当缓存清除。完整维护顺序见[维护手册](MAINTENANCE.zh-CN.md)。

## 隔离验证与实际边界

- 固定 Windows sing-box 1.14.2 和 Mihomo 1.19.32，三种拥塞控制 × 两种 UDP 中继均执行真实 HTTPS 和代理 UDP DNS。
- 两个用户分别鉴权；错误 UUID、密码、SNI 以及不受信任证书使用反例验证。连续 HTTPS 响应、传输 UDP 中断而 TCP 诱饵仍开放、恢复后重新可用，以及错误 DNS ID 不得算作回程证据均有回归。
- Debian 12／13 各在全新、带身份标记的隔离虚拟机完成 20 项生命周期断言，包含两用户、两种中继配置、共享证书、SS2022 同机保留、防火墙、密码／UUID 轮换、换证、停用／启用、应用 UDP 阻断后的失败恢复、确认丢失核对、重启、双客户端生成与移除。
- 原生 WinUI 后台实例验证默认值、边界错误、用户 UUID 与密码字段、UDP 中继选择、审阅不泄露密码及取消不保存；前台激活与前台采样为零，测试实例已关闭。
- Python 主机适配器验证 UDP 端口冲突、TCP 同端口不冒充 UDP、监听 PID 归属，源配置与恢复边界继续复用既有回归。

完整 .NET 回归通过 2433 项断言，随后新增的共享核心升级范围、缺少 UDP 证据时恢复原核心、升级成功记录版本三项断言，在 30 项 TUIC 模型与生成专项回归中通过。项目主回归通过 956 项主断言，交互、工作台、更新、审计及 Python／Bash 检查亦通过；固定双客户端兼容和各 16 项实际分流检查、613 个文本文件的秘密扫描通过。Debian 的 20 项 × 两版本、原生 WinUI 的七项结果分别保留，不混算成公网验收。

Windows 没有符号链接创建权限的两项通用检查按既有规则跳过，Unix CI 仍负责对应分支。编译成功，但 NuGet 漏洞源暂时不可达并产生 NU1900 警告；本轮不能据此宣称重新完成依赖漏洞扫描。

Windows→WSL 虚拟机测试桥封装测试数据报，WSL→来宾使用真实 UDP；来宾实际运行 systemd、nftables 和固定协议核心。Windows 原生回环 QUIC 另行覆盖。公网线路、服务商安全组和完整 IPv6 联网本轮未做生产验证，IPv6 节点投影不能替代这些结果。

### 短时资源观察

使用 cubic，在同一 Windows 合成服务器依次运行两个客户端、两个 UDP 中继模式。工作负载相同：HTTPS 连续返回 18 × 4096 字节；排除头两秒 RSS 样本。单位 MiB，CPU 按单逻辑核 100% 计算：

| 客户端／中继 | 秒／RSS 样本数 | 客户端 RSS 中位数／P95 | 服务端 RSS 中位数／P95 | 客户端／服务端 CPU |
| --- | --- | --- | --- | --- |
| sing-box／native | 17.03／16 | 36.91／36.91 | 37.04／37.05 | 本次计时粒度未记到增量／同左 |
| Mihomo／native | 20.53／17 | 33.28／33.28 | 37.86／37.86 | 0.23%／0.23% |
| sing-box／quic | 17.02／16 | 37.50／37.56 | 38.75／38.75 | 本次计时粒度未记到增量／同左 |
| Mihomo／quic | 22.83／17 | 33.14／33.14 | 40.25／40.25 | 0.07%／0.21% |

该工作负载不比较公网吞吐。服务器连续运行，缓存、执行顺序和采样粒度影响数值；Mihomo 的完成时间也不据此推断通用性能优劣。当前能确认复用了既有每入站一个核心的架构，没有额外常驻控制层，所有测试核心与虚拟机均已关闭。短测不能证明长期内存稳定性，也不能宣称协议比其他协议更省资源。
