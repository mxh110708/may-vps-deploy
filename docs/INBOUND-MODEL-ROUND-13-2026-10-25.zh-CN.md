# 原定第十三轮：通用多入站资源模型

日期：2026-10-25。本文对应原计划的第十三轮，不是 May Monitor M2 的旧编号。源码与验证范围见下文；本轮不发布、不安装桌面更新、不改生产 VPS。

## 本轮实现范围

在实例页进入「通用多入站 → 管理入站」。新增入站使用稳定身份，名称不参与文件路径和服务身份；同一实例可以维护多个同协议或不同协议的入站。当前协议为 VLESS / Reality（固定 Xray 核心）、AnyTLS（可带 ECH）和 Shadowsocks 2022 AES-128/256（固定 sing-box 核心）。

| 资源 | 管理内容 | 关联与修改效果 |
| --- | --- | --- |
| 入站身份 | 稳定 ID、名称、协议、启停 | 新入站分配身份；原身份不能直接改成另一协议。仅改显示名称不重启服务。 |
| 监听 | 每个入站独立 IP 与端口 | 支持 IPv4、IPv6 与通配地址；保留停用入站的端口，防止其他组件占用。 |
| 用户 | UUID、密码或 SS2022 用户密钥 | 入站引用一至多个兼容用户；同一用户可被多个入站引用。修改共享凭据会纳入全部受影响入站。 |
| 证书 | 独立证书身份、证书链与私钥、摘要、到期时间 | AnyTLS 引用证书；导入时核对密钥匹配，启用时检查有效期和 SNI。替换共享证书只影响引用者。 |
| 出站 | IPv4 / IPv6 / 自动直连，或已有方案中的代理节点 | 每个入站选择一个出站身份；共享出站变化会显示全部影响范围。代理来源保留鉴权、TLS、SNI 等已有参数。 |
| 恢复范围 | 本次变更的入站 ID 集合及公共目录 | 只停止、替换和恢复这些入站的配置与服务；不重启未受影响的入站。公共目录也必须满足原／新摘要边界。 |

每实例最多 16 个独立入站，每入站最多 32 个用户，每类关联资源最多 64 个。仍被引用的用户、证书、出站不能直接删除。删除入站不隐式删除其他入站引用的共享资源；不再使用的资源由维护者显式移除。

旧的 Reality／AnyTLS／Shadowsocks 固定角色服务继续使用原维护入口，在新界面列为现有组件。**本轮不会自动迁移或重建旧服务**。这避免为引入数据模型而改变现有生产连接；新协议后续按新模型接入。

## 使用流程

1. 选择已经部署或接入成功的实例，确认 SSH 和备用管理入口可用，且没有未完成事务。
2. 进入「管理入站」，在「入站与监听」添加协议，填写监听和协议参数。Reality 可由固定核心生成密钥；SS2022 的服务器密钥独立于用户密钥。
3. 在「用户与凭据」添加、查看引用或轮换凭据，再回到入站勾选需要的用户。用户类型须与协议一致，不能把 AnyTLS 密码用户用于 VLESS 或 SS2022。
4. AnyTLS 在「证书」导入已申请的证书链与匹配私钥，在入站中选择证书和 SNI。若需要 ECH，按 SNI 生成配套材料后启用。证书申请、DNS 修改、自动续期不属于本轮新模型；旧服务原有 Certbot 流程不变。
5. 在「出站」建立直连或选择已保存的代理节点。Reality 当前复用既有 Xray 的 Shadowsocks／SS2022 下一跳模型；AnyTLS／SS2022 可使用支持的 Shadowsocks、VLESS 或 AnyTLS 原生节点。可指定出口地址族和预期出口 IP；若只填地址族，则实际验收观测对应地址族，不据此推断具体运营商或地理位置。
6. 点击「审阅」，核对所有入站的用户、证书、出站、监听、启停和本次影响范围。新监听的来源范围由监听地址、系统及服务商防火墙决定，协议用户负责鉴权；新模型不继承旧落地的来源白名单。
7. 确认后执行五阶段：预检 → 本次范围快照 → 应用 → 实际用户代理 HTTPS 验收 → 提交。取消、验收失败或远端结果不明时沿用同一事务的核对与恢复流程，不重放写入命令。
8. 使用「只读检查已保存模型」核对实际文件、服务和每个启用用户的连接。该操作不提交表单中尚未保存的草稿，也不会主动启停服务。最近检查失败后，对应来源停止作为可用节点导出，重新检查成功才能恢复。

修改显示名称或未引用资源不会重启正在使用的入站；端口、鉴权、TLS、实际出站及出口验收条件的变化会重新验收对应入站。共享资源有多个使用者时，审阅会同时列出这些使用者，不能只勾选其中一部分跳过必要恢复范围。

## 客户端与来源一致性

配置设计增加「添加独立入站节点」。按入站、用户和服务器连接地址族分别生成节点，支持选择入口地区组。节点保留独立来源身份；后续更新已有节点时保留其用户自定义名称和地区归属。

生成 Clash / Mihomo 与 sing-box 配置前重新核对来源：入站启用且最近运行状态正常、用户仍被引用、当前凭据／证书／出站对应的连接及资源摘要匹配，并有相应用户和地址族的实际验收。停用、删除、轮换、证书或出站变化，以及未确认恢复，都会使旧来源失效。仅更换显示名称不使旧鉴权失效。

代理出站通过加密方案中的节点引用及其摘要解析，不把密码复制到公共计划。来源变化后须重新选择审阅；拒绝本实例受管入站回指、自身监听环路和过深的受管来源递归。节点选择器按实例一次解密和渲染，避免对每个用户反复扫描整个模型。

本轮真实连接验收是控制端经每个启用用户和导出地址族发起 HTTPS 请求。每份证据绑定入站 ID、用户 ID、连接地址族和连接摘要；一个成功请求不能替代其他用户。它不表示吞吐、UDP、IPv6 生产线路或长时间稳定性均通过。SS2022 的 UDP 服务配置会生成，但本轮 UDP 实际验收标为 `NotMeasured`，不以 TCP 成功代替。

## 运行文件与私人材料

以下均为通用路径说明，不包含任何实例地址、端口或凭据：

| 位置 | 内容与权限 |
| --- | --- |
| 私人实例归档中的 `deployment-plan.json` → `InboundModel` | 公共资源身份、引用、协议选项；不含密码、证书私钥或 Reality 私钥。 |
| `secrets.dotnet.private.json` → `Inbounds` | Windows 控制端使用既有加密机制保存用户、证书及每个入站的私密材料。 |
| `deployment-state.json` → `Inbounds` | 已应用模型、核心固定身份、运行与配置摘要、按入站保存的验收证据。 |
| `/etc/may-inbounds/model.json` | 远端目录、配置摘要、核心引用；root 私有。 |
| `/etc/may-inbounds/<inbound-id>.json` | 单入站运行配置，包含该入站需要的鉴权与 TLS 材料；root 0600。 |
| `/etc/systemd/system/may-inbound-<inbound-id>.service` | 独立服务，使用 `DynamicUser`、只读系统与 `LoadCredential` 读取配置；单元文件不写入密钥。 |
| `/usr/local/lib/may-inbound-cores/<archive-sha256>/` | 官方归档校验通过后的固定 Xray 或 sing-box 核心及安装记录；不替换旧角色核心。 |
| `/root/vps-deploy-backups/<timestamp>/protocol-lifecycle/` | 本次范围快照、固定恢复程序和事务材料；需按私人材料管理。 |

固定核心按归档摘要共享，避免每个入站复制可执行文件；已有目录或程序不匹配时拒绝覆盖。应用更新不会偷偷改变已应用入站的核心版本。新核心缓存校验成功后即使本次配置回退也可保留，它不代表存在活动服务。

每个入站是一个独立进程，换取明确的启停和恢复边界；这不是进程内多入站的内存优化。本轮没有增加持续轮询的后台控制器，也没有声称降低服务器内存。后续若合并进程，需另外验证重载、影响范围和资源收益，不能以节省进程数破坏隔离。

## 事务、恢复与冲突保护

- 审阅绑定实例材料、加密来源文件及本轮远端脚本摘要；审阅后变化需要重新审阅。
- 远端预检核对整个已保存目录及核心身份、systemd 单元来源与覆盖配置、实际本机地址和监听冲突。
- SSH、旧协议、TCP／UDP 转发和监控端口双向保留；旧协议追加安装及恢复也不能占用独立入站端口。
- 配置先经固定核心检查，再停止受影响的服务；启动后等待 TCP 监听就绪，再进入实际用户验收。就绪检查本身不是协议验收。
- 快照只包含受影响入站的运行文件、单元和公共目录。恢复前检查未受影响文件、已知原／新文件摘要、归档成员及服务范围；出现未知身份、外部修改、链接或覆盖配置时停止恢复，不覆盖它们。
- 复用既有 SSH 管理验证、事务身份与回滚定时器。丢失提交响应时先核对同一事务状态；远端已提交则报告确认丢失后的已完成，不重复安装或回放。
- 未移除的独立入站阻止实例退役和私人归档删除；停用也保留管理与恢复责任。
- 普通健康审计纳入独立入站的配置与启停状态，但不把这项只读审计当成新的应用层验收。

「恢复」在本轮指未完成变更的同范围自动／人工核对恢复，**没有新增历史版本任选回退或跨实例分布式入站事务**。已提交后若要恢复旧配置，应重新审阅该配置并做新的变更和验收；不能拿旧快照直接覆盖目前的其他资源。

```powershell

python tests/test_inbound_host.py
```

固定 Xray 实际配置检查使用显式 `MAY_TEST_XRAY` 测试运行时；没有配置该运行时的环境会明确跳过该项，不把跳过写成通过。本轮 Windows 测试配置了官方固定版本及其二进制摘要检查。NuGet 漏洞元数据源在本地不可达，测试项目构建出现 NU1900 警告；没有据此声称完成依赖漏洞扫描，也没有更换依赖版本。

Linux 权限、链接与服务语义使用 Linux 临时目录和带 DMI／标记核对的全新 Debian 12／13 虚拟机；Windows 挂载盘的权限映射不能替代 Linux 0600 检查。`tests/inbound-vm-fixture.py` 与 `--inbounds-vm` 是显式隔离测试入口，不接受生产路径作替代。虚拟机通过控制端回环端口映射；TLS 测试 CA 仅注入测试进程，不安装到操作系统信任库。测试完成须停止虚拟机。

原生界面用合成私人工作区和专用测试管道运行 `suite.inbounds`；窗口隐藏，不抢焦点、不注册托盘、不注入用户鼠标或键盘。它验证表单和审阅行为，不授权应用生产配置。

初版试验曾让所有入站共用 sing-box 服务端。真实 HTTPS 测试中 Reality / Vision 出现间歇失败，同一路径的 curl 可成功；上游也有[额外 TLS 记录的报告](https://github.com/SagerNet/sing-box/issues/4404)，但本轮没有据此宣称确认上游根因。最终 Reality 延续项目已有的固定 Xray 服务端选择，客户端和 TLS 校验保持原标准，补测连续多次 HTTPS 请求。没有通过重试失败请求或降低 TLS 校验来认定通过。

## 后续边界

原计划第十四轮仍是 Hysteria2 的完整部署、维护、双客户端及真实连接闭环。本轮没有把客户端已认识某协议等同于已实现服务端功能，也不扩展 TUIC、在线订阅托管、计费或用户流量配额。旧角色的主动迁移、证书自动续期、独立入站的完整 UDP 实际验收及跨实例共享事务，分别按后续需求评估。

协议字段参考：[sing-box VLESS](https://sing-box.sagernet.org/configuration/inbound/vless/)、[Shadowsocks](https://sing-box.sagernet.org/configuration/inbound/shadowsocks/)、[TLS](https://sing-box.sagernet.org/configuration/shared/tls/)。实际兼容性以仓库固定核心的配置校验和真实连接结果为准。
