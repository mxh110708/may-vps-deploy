# 第十五轮：Hysteria2 分享与端口跳跃

本轮完善第十四轮已有的 Hysteria2，不增加其他协议。源码功能已实现；当前发行基线仍是 v0.9.38，本轮尚未打包、推送或发布。以下操作针对包含本轮改动的构建，不能据此判断已安装版本具备这些入口。

## 功能和使用方式

### 导入、分享与订阅来源

配置设计的节点导入支持 `hysteria2://` 和 `hy2://`。不填写端口时使用 443；鉴权、SNI、IPv6、显示名称和 Salamander 参数会对应写入 Mihomo 与 sing-box。鉴权值作为一个整体做 URI 百分号编码，不能把密码中的 `:`、`@`、`#` 或 `+` 当作额外字段分隔符。

标准多端口写在服务器地址的端口部分，允许逗号分隔和连字符范围。下面只说明格式，所有尖括号项均须替换；不是可直接连接的节点：

```text
hysteria2://<百分号编码的鉴权>@<服务器>:<主端口>,<其他端口范围>/?sni=<证书域名>&insecure=0#<百分号编码的显示名>
```

选择节点后使用原有分享预览，可输出纯文本或 Base64 列表；原有订阅来源预览和刷新同样使用新解析器。分享前检查两类客户端的连接参数相同，并将完整链接重新解析核对；不只检查 URI 是否能解析。

标准 URI 没有本项目可互通保留的固定带宽、自定义跳跃间隔、证书信任材料、ECH 等全部高级配置。遇到这类节点，预览会说明不能完整分享，要求导出完整客户端配置。不会静默删除参数，也不会为使导入成功关闭 TLS 验证。本轮仅支持 Salamander，不接受 Gecko、Realm、非标准 `mport` 查询参数或未知扩展。

链接、订阅及完整配置均含可使用的凭据；预览和来源记录不保存原始链接，导出的文件仍应按私人材料保管。

### 受管入站的端口跳跃

在「实例 → 通用多入站 → 管理入站」选择 Hysteria2，勾选「启用端口跳跃」。填写端口集合和间隔，再正常审阅与执行。

| 参数 | 约束与两端关系 |
| --- | --- |
| 原监听端口 | 服务实际绑定的唯一 UDP 端口，须包含在跳跃集合中。 |
| 跳跃端口 | 逗号分隔的端口／范围，端口为 1–65535；至少两个不同端口，每个受管入站最多 256 个，最多 32 段。重叠范围合并。 |
| 跳跃间隔 | 5–3600 秒的整数，默认 30 秒；Mihomo 使用 `hop-interval`，sing-box 使用 `hop_interval`。 |
| 主机防火墙 | 需要现有受管 nftables；保留现有防火墙模式不会自动接管或添加跳跃。 |
| 服务商安全组 | 必须允许整个集合的 UDP；应用不会更改服务商网页或 Cloudflare 设置。 |

Mihomo 输出 `ports`，sing-box 输出 `server_ports`。两者均指向同一个经过鉴权的 Hysteria2 服务。主机在自有 `inet filter` 表内以 prerouting NAT 将其他端口重定向到原监听，不新增代理进程、定时器或逐端口常驻监听。设置只在明确保存、检查与生成候选时处理。

通配监听使用本机端口重定向；绑定具体地址时使用保留该地址的 DNAT，避免多地址主机被重写到网卡的其他默认地址。

所有跳跃端口都参加 SSH、固定角色、通用入站与 TCP／UDP 转发的冲突检查。停用入站仍保留端口；移除跳跃设置或入站后才释放。远端还会检查地址归属及每个替代 UDP 端口是否已被其他进程占用。

跳跃集合或间隔变化会使连接来源身份和旧验收失效，需要重新验收并生成客户端文件；不会把旧候选当成新设置。默认 30 秒间隔可按标准 URI 分享，自定义间隔须导出完整配置。

## 验收、失败和恢复

1. 预检核对服务器身份、当前入站／服务归属、端口及自有防火墙与归档的一致性。已有未知规则或文件变更先停止。
2. 快照范围为受影响入站和自有防火墙。应用使用单次 nftables 事务重建经过核对的自有表，清理已停用的跳跃链，不清空其他表。
3. 按用户与地址族分别执行真实协议鉴权和代理 HTTPS。每个启用的跳跃端口另做确定性的固定端口请求；不能随机成功一个端口就宣布整个集合通过。同一次验收内，相同入站／地址族共享端口可达性结果，但每个用户仍独立鉴权。
4. 端口检查有取消和五分钟阶段预算。缺少完整端口结果、错误协议、失败或超时不能提交，也不能导出为已验收来源。
5. 应用失败按原事务恢复；不重启未受影响入站。取消／确认丢失沿用既有恢复与状态核对，不重放不明写入。
6. 停用或移除后不保留跳跃链；重新启用和整机重启后，原服务和持久化防火墙应继续匹配。只读检查也会核对启用的跳跃映射。

原普通 Hysteria2 模型不自动增加跳跃字段，不改既有单端口默认行为。原有用户、证书、出站和多入站资源模型继续使用。

仓库 `ValidateProject` 通过；.NET 全量 2303 项断言通过，随后补充的验收适配器用例纳入第十五轮 85 项专项断言并通过。Python 入站 24 项、跳跃防火墙 7 项、跨功能恢复 17 项以及审计 60 项通过；固定双客户端兼容性与实际学术路由测试通过。Bash 语法、ShellCheck warning 级和公开文件秘密扫描通过。Windows 无符号链接权限及未启用的 Xray 原生补测仍按测试输出标为跳过，不计作本轮通过；NuGet 漏洞数据源不可达产生 NU1900，不能据构建成功宣称完成依赖漏洞扫描。

Windows→WSL 的虚拟机测试桥把测试数据报封装在鉴权回环通道中，WSL→来宾使用真实 UDP，并实际经过来宾 nftables。它不代表 Windows 到公网的原生 UDP 路径；Windows 原生回环 QUIC 由单独的双客户端测试覆盖。IPv6 的模型、映射生成与地址族分离有回归，来宾本轮完整生命周期使用 IPv4，不能据此宣布公网 IPv6／服务商 NAT 已通过。

首次 Debian 环境的在线依赖下载失败，未作为功能通过依据；之后在全新镜像使用官方索引 SHA256 核对的离线依赖完成验证。实测发现 `flush table` 保留空 base chain 的问题后，修复为自有表原子重建，并从新镜像重新跑完两套生命周期。失败记录仍保存在本轮临时证据中。

### 资源观察

同一 Windows 合成服务，串行执行相同 18 × 4096 字节 HTTPS 响应；每阶段约 17 秒，RSS 排除前两秒，均为 16 个样本。客户端为分别启动的固定核心，服务端在四阶段间连续运行。单位 MiB，CPU 以单逻辑核 100% 为基准：

| 客户端／模式 | 客户端 RSS 中位数／P95／峰值 | 服务端 RSS 中位数／P95／峰值 | 客户端／服务端 CPU |
| --- | --- | --- | --- |
| sing-box 普通 | 37.61／38.23／38.23 | 37.02／37.71／37.71 | 0.09%／0.09% |
| sing-box 跳跃 | 38.16／38.16／38.16 | 38.35／38.35／38.35 | 本次计时粒度未记到增量／同左 |
| Mihomo 普通 | 32.78／32.78／32.78 | 39.43／39.44／39.44 | 0.09%／0.09% |
| Mihomo 跳跃 | 33.08／33.08／33.08 | 40.09／40.56／40.56 | 本次计时粒度未记到增量／0.92% |

这是短时功能负载观察，不是吞吐基准或长测。连续服务的缓存和阶段顺序会影响 RSS，不能把阶段间差值全部归因于跳跃，也不能把零 CPU 计时增量说成无开销。当前能确认的是复用了同一服务与监听，未增加常驻进程；不能据此承诺公网性能提升或零内存增长。测试客户端及虚拟机均已关闭。
