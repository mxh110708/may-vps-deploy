# v0.9.16 BBR v3 与时间设置实测

实测日期：2026-10-11。只在已授权的 MOE 与 YUNYOO 专用测试机执行内核操作，非测试 VPS 未修改。所有原生界面测试通过本轮隔离应用的后台接口完成，窗口激活及前台采样均为 0；没有鼠标注入、系统代理/TUN 切换或虚拟机。

## 固定版本与恢复

MOE 使用应用固定的 XanMod LTS `6.18.55-x64v1-xanmod1`。核验官方 InRelease 签名、Packages 索引链、具体包大小/身份与 SHA256，实际安装一个内核镜像，原有 `6.1.0-44-cloud-amd64` 继续运行。

首次下载遇到官方仓库对默认 Python 请求头的 HTTP 403。保留失败事务，确认旧内核和启动设置后显式结束准备；修正为 Debian APT 请求头，再审阅另一事务。没有取消签名或哈希检查，也没有重放失败的安装事务。

| 情况 | 实测结果 |
|---|---|
| 独立安装任务完成前丢失准备应答 | 应用保留待核对状态；VPS 独立任务安装成功，执行计数为 1；重新打开后读取为 Prepared，没有重复安装 |
| 请求单次新内核启动后丢失应答 | 应用保留恢复屏障，重新读取启动身份与运行内核，没有重发重启 |
| 新内核验收 | 真实 TCP_CC_INFO 版本为 3，原服务正常，主/救援端口的 root 与管理用户 sudo 连接均通过 |
| 提交应答丢失 | 远端已提交，重新读取同一事务为 Committed，应用记 CompletedWithWarnings；没有再次提交 |
| 显式回退 | 实际重新运行原有内核，两个内核包保留，管理连接和原服务通过；回退范围没有扩展到协议或监控配置 |
| 已保留内核再次启用后应用退出 | 发出单次重启后测试应用退出，新内核未获验收；独立保护任务在 5 分钟后回到原内核，再由应用核对为 RolledBack。没有再次安装 |

## 最新兼容 LTS

YUNYOO 通过应用“官方最新兼容 LTS”查询 Debian bookworm 的官方签名索引，核验随附签名信任锚。按 LTS x64v1 元包依赖解析并锁定具体镜像，保存查询时间、签名材料及包 SHA256，没有新增长期 APT 仓库或安装元包/头文件。

本轮查询得到的最新 LTS 与应用固定版本相同；两种选择的来源流程分别执行。最新来源实际完成单个镜像安装、独立审阅重启、真实 BBR v3 运行核验、原服务与主/救援 SSH 验收，事务为 Committed。

随后通过应用启用 fq + BBR v3 基础配置，核对实际版本、队列和管理入口。修正新内核 pfifo_fast 固定属性被误当成可写选项的问题；实际执行本轮 Network 专属恢复点，确认原 pfifo_fast 队列、固定属性与运行参数均恢复，再通过应用重新启用 fq + BBR v3。更换内核后的旧测速记录不能继续作为精细建议，界面要求重新采集并提供基础配置入口。

## 原生时间界面

最终原生实例的 11 项行为检查通过：默认原有 BBR 和固定内核来源、常用时区选择、结束 24、跨午夜、无效小时、清空自定义时区、IANA 输入、Windows 时区 ID、无效时区、从无效输入恢复预设，以及后台窗口无干扰证明。说明随实际控件事件立即更新；20–24 明确显示次日零点。

- 共享核心：603 项边界与流程断言通过；覆盖应答丢失、禁止重放、事务身份、恢复范围、未确认版本、最新查询过期和审阅后材料变化、24 点及无效时间。Windows 无链接创建权限的两项由 Unix CI 执行。

- Debian 12 上完成上述真实安装、重启及回退。Debian 13 为兼容规则与 CI 检查，未声称本轮在真实 Debian 13 上启动新内核。
- EFI/Secure Boot、容器、DKMS、LVM/加密及不明确 GRUB 布局当前明确拒绝自动升级。
- 没有故意制造内核完全无法进入用户空间的故障。该情况下自动保护服务无法运行，需服务商控制台重启；单次启动后的默认保留为旧内核。
- 本轮没有新增真实晚高峰吞吐样本，也没有补齐本机直连 IPv6 条件；这些保留此前的未完成记录。没有把 BBR v3 验收当作吞吐一定提高或丢包必然降低的证据。
