# FlyX 功能设计对照与 May Deploy 扩展建议

评估日期：2026-10-20。此文件是设计评估与实施建议，不表示功能已经实现、安装或经过生产验收。

对照基线：

- FlyX：`kure29/flyx`，提交 `13da01831f5be5b4c7d311824a20a5becd71f0aa`。阅读使用文档及链式出站、订阅处理、逐跳延迟相关源码；未运行其面板、Agent 或安装脚本，未做全面功能／安全审计。
- May Deploy：本地提交 `e81fa0462ae19860839ed362c04b05bc6fb0eaa3`。以当前 WinUI／.NET 实现为准，README 的旧版本段落不作为当前缺失功能的唯一依据。

## 结论

值得借鉴的核心是统一组织“实例、服务入站、客户端节点、线路、来源与输出”，让同一组资源支持导入、组合、诊断与生成。May 应继续采用按需启动的桌面控制端，通过现有 SSH、任务审阅、指纹校验和恢复事务扩展功能。

首轮建议做 **外部节点导入、现有连接图增强、独立线路诊断**。随后扩展输出处理规则和按需的服务器侧出站链路。大批协议、多入站、独立转发引擎及共享订阅服务适合分别立项。

## 首轮可交付范围

### 1. 外部节点导入

在现有“添加节点”中增加“粘贴分享链接”，批量导入前展示名称、协议、来源、用途、地区及兼容结果。先覆盖当前已支持的 Reality、AnyTLS、Shadowsocks／SS2022，复用现有生成和校验流程；不以加入解析器代替完整协议支持。

外部节点与受管实例来源分别记录。导入外部节点只增加加密的本地引用；删除引用不卸载服务器、不修改其密钥和监听。来源更新展示新增、删除、参数变化以及受影响的方案，确认后更新引用并使旧候选失效。

去重比较协议、地址、端口、鉴权、TLS 和传输参数；同地址同端口的不同用户仍是不同节点。显示名变化应保留稳定身份，不能因自动命名破坏线路引用。现有受管节点来源指纹继续使用。

订阅 URL 可以作为第二步输入：用户主动获取、限定响应大小／超时／重定向、支持取消、预览变更。后台自动同步和任意 JS 处理脚本不纳入首轮。

### 2. 增强连接图与依赖审阅

保留 `DesignerConnections` 的基础图和已有 `region_group`、`transit_group` 数据。在此基础上展示完整业务路径及依赖，不另建一套靠名称推断地区的配置。

对现有 LA 入口与 SF ATT IPv6 落地场景，应分别展示：入口地区、落地实例、最终出口地区、连接服务器用的地址族、落地访问网站用的地址族。地址的城市标签可人工核对，不能从机器位置或前缀自动替换已有命名。

把三种关系分开：

- 客户端链式：生成 Mihomo `dialer-proxy` 或 sing-box `detour`；现有客户端配置设计属于此类。
- 服务器转发：在中转服务器上监听并把端口流量送往目标；需要单独的远端变更。
- 服务器出站链式：入站流量由该服务器经另一代理出站；需要单独的远端路由配置。

改名、删除或替换节点前展示引用影响；不自动把缺失入口改为直连。服务商管理的 ATT IPv6 仍按既有例外处理：可记录外部出口引用及核验状态，首轮不运行或接管服务商租约脚本。

### 3. 独立线路诊断

在连接图或实例页提供“检查这条线路”。先执行有限的连通与协议检查，吞吐测试单独选择并沿用整轮预算：

| 证据 | 展示内容与边界 |
| --- | --- |
| 本机到入口 | 标记来自实际使用地；DNS、TCP、代理握手分别报告 |
| 入口到落地 | 在允许的路径上检查下一跳；标记实际发起位置与地址族 |
| 完整代理到目标 | 使用现有隔离客户端，验证真实 HTTPS 及实际公网出口 |
| 落地本机与公网 | 分开显示本机监听／源地址状态和外部访问结果 |
| 历史／回程 | 显示时间、方向、测量方法、缺测和识别依据，不只给一个颜色 |

优先把结果定位到对应跳或协议阶段，避免“端口通”“服务在运行”“HTTP 成功”统一显示为线路正常。地区测试点可按用户使用地选择，保留广东等目标的显式设置；定期采样应是可关闭、有预算且明确执行位置的后续能力。

FlyX 的线路时延是分段 TCP 测量相加的估算，文档与 `relay_latency.go` 均有说明。May 的实际端到端代理验收继续保留；估算值只能与实测分列。远端测回国内的结果也不能直接等同本机正向线路。

## 第二轮与后续能力

### 输出规则与客户端能力报告

沿用现有“方案→生成候选→核心校验→审阅→导出”，在生成前添加可预览的筛选、显示名替换、前后缀及排序。模板继续保留用户的 DNS、TUN 和自定义规则。需要再支持其他客户端时，为协议、TLS／ECH、UDP、规则格式和链式能力逐项列出支持情况。

不支持的字段或链式关系应明确阻止相应输出，或要求用户显式移除／修改；不要静默丢参数。通用分享链接不能表达完整链路时，应说明限制，不能自动输出为等效直连。空组应提示处理，不能自动落到 `DIRECT`。

若以后需要可订阅 URL，再选择单独的、明确部署的发布服务。订阅取件令牌与代理鉴权凭据分别管理；已有方案文件不能仅靠增加 HTTP 链接就变成安全的在线订阅服务。

### 服务端链式与独立转发

先提供一个受支持入站的固定下一跳，审阅中显示源入站、目的节点、受影响服务、防火墙变化及恢复点。后续再增加有限的域名／网段规则和独立端口转发。

新增转发组件时核对协议能力、TCP／UDP、监听范围和端口冲突；由本组件管理的配置及防火墙规则限定归属。跨实例操作分阶段核验和提交，远端回复丢失先对账，不盲目重复写入；继续保留 SSH 恢复通道和其他受管组件。

### 多入站与协议扩展

当前 `DeploymentPlans.Roles`、`ProtocolInventory`、端口字段和 `ClientProfiles.Nodes` 体现的是固定角色模型。多入站扩展应建立独立入站 ID，将内核版本、监听、证书、用户、出站和恢复范围关联到该入站；不能仅在协议下拉框中再加名称。

Hysteria2 可作为 UDP 协议扩展候选，TUIC 作为后续候选。每项都需要服务端部署与升级、端口／UDP 可达性、TLS、两个客户端生成与真实连接、取消／回滚验证。Snell、NaïveProxy、ShadowTLS 等按具体客户端需求增加，不以协议数量作为本轮目标。

## 实施顺序与验收

1. **先补导入和预览。** 保持当前支持的协议；验证链接解析、错误逐项反馈、凭据不泄露、稳定身份、同端口不同用户及来源刷新后旧候选失效。
2. **增强现有连接图。** 验证入口和出口地区独立、地址族区分、孤立／循环依赖、删除影响与未受管资源边界；只编辑本地方案时不连接服务器。
3. **增加独立诊断。** 复用 `NetworkPaths`、`NetworkSelection`、`NetworkMeasurement` 和客户端校验资产；验证测量位置、真实出口、缺测、取消、时限与共享流量预算。模拟通过与真实 VPS 验收分别记录。
4. **扩充生成处理规则。** 对两类目标分别做能力报告、预览、真实核心解析及导出事务恢复。
5. **分别实施远端路由／转发及新协议。** 每项有单独计划、审阅、变更范围和验收；按现有任务状态机处理失败与回复不明。

前三项可作为首轮完整扩展，不需要新增常驻面板、Agent 或监控数据库。Route 继续负责客户端运行时的自动故障切换；Deploy 负责配置设计、按需诊断与远端操作。
