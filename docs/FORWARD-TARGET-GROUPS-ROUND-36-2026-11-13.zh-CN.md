## 支持范围

每条独立转发规则可选择普通单目标，或一个主目标加一个备用目标。上方原目标始终为主，备用单独填写字面 IP 和端口；顺序不会随一次延迟变化而重新排列。监听地址族、目标地址族彼此独立，备用可使用 IPv6。

| 转发类型 | 健康确认及实际验收 |
| --- | --- |
| TCP TLS | VPS 分别向主备建立 TLS 连接，验证系统信任链与声明的 SNI；控制端仍经实际转发监听完成 TLS 验收。 |
| TCP SSH | VPS 分别核对完整 SSH 2.0 协议响应；控制端经监听验证相同响应。该探测没有登录，也不核实 SSH 主机公钥。 |
| TCP 代理来源 | 继续选择已保存原始代理，保留完整鉴权、TLS、传输和会话参数。VPS 健康只检查主备 TCP 连接可达性；控制端经当前实际入口执行原协议及 HTTPS 出口验收。 |
| TCP PROXY v1／v2 | 保留原显式输出。主备健康也先发送声明的头，再校验 TLS；不接受或信任客户端提交的 PROXY 来源。 |
| UDP DNS | 分别取得匹配新事务、完整问题和有效记录的 DNS 回答；控制端仍经监听完成真实数据报往返。 |
| UDP 回显 | 每次使用新随机内容，要求目标原样返回；控制端也验证经实际监听的回程。 |
| UDP Shadowsocks／SS2022 | 原单目标功能保留；本轮不为其启用自动主备，因为工作进程没有足以验证加密代理 UDP 的明文健康凭据。不会改用 TCP 健康替代。 |
| 跨实例编排／WireGuard | 已固定的线路和依赖保持原范围，不能把主备字段混入线路所有的转发规则，或暗中切换其落地。 |

代理主备必须提供可使用同一客户端参数的服务。该组不能表达两套不同 UUID、密码、Reality 身份或下载参数；两台 TCP 端口都可连接并不证明两端代理鉴权一致。因此，TCP 可达但鉴权失败、应用卡顿或出口异常，不会由此探测自动判为主目标失效。未来若增加协议健康，必须单独设计凭据范围、验证成本和结果语义。

主备的实际出口可能不同，代理验收及派生节点保留原出口地址族，不继续把主目标的单一预期出口地址套用到备用。鉴权、SNI、证书与传输参数保持原样。生成 Shadowsocks 转发节点时，带 TCP 主备的规则不会自动绑定原单目标 UDP 规则，避免两种传输实际走向不同；该派生节点明确为仅 TCP。

## 判定规则

| 参数 | 默认值与边界 |
| --- | --- |
| 主／备 | 原 `TargetAddress`／`TargetPort` 为主；`TargetGroup.BackupAddress`／`BackupPort` 为备，不得重复。 |
| 探测间隔 | 默认10秒，5–300秒。 |
| 单目标超时 | 默认3秒，1–10秒；间隔至少容纳主备两次超时。两次探测有总时限，不无限等待。 |
| 连续失败确认 | 默认3次，2–10次；一次成功会清零该目标的失败计数。 |
| 连续恢复确认 | 默认3次，2–10次；一次失败会重置连续恢复。 |
| 首选恢复持续时间 | 默认30秒，10–600秒；同时满足连续恢复次数和持续时间才自动回切。使用 monotonic 时间，不受系统墙钟校正影响。 |
| 自动返回首选 | 默认开启。关闭后，备用健康时继续使用备用；备用失效时才选择已恢复健康的主目标。 |

首次激活没有既有选择，按主→备选择本轮探测通过的第一个目标；这与运行中切换的连续失败门槛分别处理。运行中的主目标达到失败门槛后，只能选择健康备用。两端均不健康时不建立新的目标连接，不改为直连或未配置的地址。

稳定恢复需要完整持续窗口。一次成功、一次低延迟，或两次成功之间夹杂失败，都不能提前返回首选。这里没有学习基线、权重或最小延迟排序。

## 连接与生命周期

自动切换只改变后续新建目标连接：

- 已建立的 TCP 流保留原目标，直到应用自行结束或连接失败。工作进程不会将已发送的字节复制到另一个目标，也不会重做应用请求。
- UDP 会话固定到原目标。确认该目标不健康后关闭相应会话；后续数据报可建立备用会话，之前的数据报不跨目标重发。回切时保留仍健康的备用会话。
- 服务端状态不会使远端应用会话跨机器迁移。QUIC、登录及长连接业务可能仍需客户端重连。
- 所有选择和探测在 VPS 工作进程中完成，关闭 Deploy 不会停止已激活组的判断。没有连接／会话后，工作进程按原60秒空闲边界退出，监听保留；下次激活重新从明确顺序选择，不保存跨进程健康计数。

原单目标 TCP 继续使用 systemd-socket-proxyd，原 PROXY 和 UDP 功能保留。主备使用 socket 激活的 Python 标准库工作进程、动态用户和有限连接／会话；TCP最多256连接、每方向64KiB用户态缓冲，组进程内存上限96MiB。UDP沿用会话上限和来源白名单。这些是资源上限，不是整应用内存优化收益。

正式组件配置仍为 root 私有文件。服务使用 systemd `LoadCredential` 将只读配置副本交给动态用户，不扩大原文件权限。运行状态写在该规则独立的 RuntimeDirectory；状态绑定完整规则摘要和采样时间。未启动、过期或损坏的报告分别保留为未知／陈旧状态，不能显示为当前健康。此方式依据 [systemd 252 凭据说明](https://www.freedesktop.org/software/systemd/man/252/systemd.exec.html#Credentials)。

## 使用步骤

1. 在实例详情打开「管理转发」或「管理 UDP 转发」，先填写原目标、监听、来源白名单及实际验收方式。
2. 勾选“使用显式主备目标组”，原目标为主；填写备用 IP 与端口。同机端口回指、重复端点、未知字段及不支持的健康组合均会被拒绝。
3. 设置失败确认、探测超时、恢复次数、持续时间和是否自动返回。健康方式跟随声明服务，不提供跳过证书校验的开关。
4. 代理类规则核对主备服务使用同一套连接身份。不能仅因为名称相似，就把另一套鉴权或传输不同的节点填作备用。
5. 审阅主备顺序、健康含义、恢复条件、监听与防火墙范围。取消不会保存规则或创建任务；重新审阅会固定备用、参数和工作程序摘要。
6. 新保存的组要求主备两端均通过本次 VPS 健康探测，且真实入口验收通过。仅写出单元、端口监听或其中一端可用不能完成新组应用。
7. 此后可选择“只读检查已保存转发”。检查同时核对实际归属、当前入口和逐目标健康；组已降级到健康备用时不强求故障主目标成功。界面展示上次检查快照，不将其当作实时面板。
8. 修改主备、健康参数或来源后重新审阅与验收。完整规则摘要进入派生节点的来源资格；备用变化后不能继续使用旧资格。

保存配置仍会重建本组件监听，可能中断现有转发连接／UDP会话。这个显式维护过程与运行中的自动选择不同，不承诺配置更新无中断。移除组可取消主备并保留普通规则；移除组件仍使用原独立操作。

## 验证、失败与恢复

主备有限探测绑定当前转发资源摘要、完整规则摘要、目标序号、地址、端口和健康方式。C# 与 Python 使用相同的类型化摘要编码，包含 Unicode 和转义字符串，避免序列化差异。缺少一端、目标被替换、证明来自旧配置或明确结果缺失都会被拒绝。

| 异常 | 行为 |
| --- | --- |
| 首次保存时备用健康不通过 | 不提交新组，按本次原快照恢复。 |
| 运行中主目标连续失败 | 达到门槛后为新连接选择健康备用，不重放应用数据。 |
| 首选恢复存在抖动 | 重置连续成功与持续窗口，继续使用健康备用。 |
| 两端均失效或健康状态陈旧 | 新连接／会话失败关闭，没有直连回退。 |
| 来源、规则、备用或程序在审阅后变化 | 审阅失效，重新读取。 |
| 取消、应用失败或确认丢失 | 使用原任务身份核对和原组件恢复点，不自动重放写入。 |
| 恢复期间出现外部文件变化 | 保留恢复材料并拒绝覆盖，不能借主备操作接管未知资源。 |

恢复范围包括本组件配置、监听单元、白名单及本次工作程序；必要时包含原受管防火墙范围。状态文件是有时效的运行观测，不作为可恢复配置，也不复制旧健康计数。另一转发组件、代理服务、SSH、监控和借用的 WireGuard 不纳入此变更。

## 权重与负载的评估

本轮不把备用当作同时分担流量的节点。权重、轮询或最少连接会引入多个同时有效去向、UDP会话粘滞、各目标独立身份／出口、容量和故障恢复后的再均衡问题，需要相应验收，不能在两个地址后直接增加一个“权重”字段就视为完成。

后续有真实并发分担需求时，再确定协议、会话保持、每目标容量与统计成本，分别设计权重及负载策略；不会自动替换本轮的明确主备。第37轮诊断工作台和第38轮客户端模板库仍按原编号执行。
