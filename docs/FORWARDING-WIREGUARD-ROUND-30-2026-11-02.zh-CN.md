# 第三十轮：双段 WireGuard 与明确的转发映射

发行更新（2026-11-03）：本轮随 v0.9.41 汇总发行；下文保留实施当时的未发行状态和测试边界，发行验证见 [v0.9.41](TESTING-0.9.41.zh-CN.md)。不代表已安装或应用到生产。

日期：2026-11-02。承接第二十四轮通道引用及共享实例多线路，实现两个相邻加密段的整链使用，补齐有限多入口／多目标和 PROXY 输出。当前为未发行源码；已发行基线仍为 v0.9.40。本轮没有推送、发布、安装桌面更新或修改生产服务器。

## 支持范围

| 场景 | 本轮行为 |
| --- | --- |
| 前置 → 中转 → 落地 | 三台不同的受管实例；可以分别选择原生连接、一段 WireGuard，或两段同时使用 WireGuard。 |
| 两个通道共享中转 | 每台最多两个独立槽位，各有接口、UDP 端口、密钥、配置、systemd 单元及恢复范围。通道之间不共享 `/32` 内层地址。 |
| 代理业务 | 沿用原生 TCP 代理与固定端口 Hysteria2／TUIC v5 UDP 的既有来源和双客户端输出；不改变落地的鉴权、SNI、协议或预期出口。 |
| 多入口／多目标 | 每条规则或线路明确绑定一个监听端口和一个目标。允许多个端口到同一目标，也允许各端口到不同目标；实例可以复用，依赖和验收按线路隔离。 |
| PROXY | 独立 TCP 转发可显式发送 v1 或 v2；v2 限 TCP 地址信息，不发送 TLV。限 TLS 证书握手验收，目标必须明确支持对应头部。 |
| 规模 | 每台两个 WireGuard 槽位、每种转发组件最多16条规则、每台最多32条线路依赖；停用规则仍占身份和端口名额。 |

同一端口按 SNI／内容选择多个目标、负载均衡、任意深度图、PROXY 输入解析、UDP PROXY、默认路由 VPN、NAT 及自动公网回退不在本轮范围。多目标通过独立映射表达，不按失败情况偷偷更换落地。

## 两个相邻通道如何连接

```text
客户端
  │ 原协议／TLS／QUIC
前置 ── WireGuard A ── 中转 ── WireGuard B ── 落地
          两端 /32              另两端 /32
```

中转的两个通道各有自己的本地内层地址。它接收经 A 转发的代理连接，再通过 B 的对端地址建立连接；不需要为两段增加内核 IP 转发、默认路由或桥接。每个内核接口只添加自己的对端 `/32` 路由，不能把另一通道地址当作自身 AllowedIPs。

两段的外层地址族分别记录，和客户端入口地址族独立。内层仍为 RFC1918 IPv4；客户端 IPv6 不表示内层已经支持 IPv6。落地须监听所选内层连接地址，不能把只监听公网 IPv6 的服务当作可从内层 IPv4 使用。

隧道对端继续具有访问本机既有监听服务的信任范围。只能选择可信受管实例，并按监听和业务白名单控制服务访问。多网卡机器还须有正确的外层往返路由；本功能不会替代其路由管理。

## 建立和选择两段加密

1. 先确认三台实例均已接入，SSH 主机身份、管理连接和恢复入口可用，没有待恢复事务。
2. 在前置「管理隧道」建立前置与中转之间的通道，并完成双向 TCP／UDP 随机挑战。
3. 在中转「管理隧道」新建中转与落地之间的通道。界面优先选择空闲槽位，建议独立端口及未占用内层地址；第二端已有通道时也选择空闲槽位。审阅两端的实际槽位、端口、地址、MTU、保活和防火墙范围后执行。
4. 两段使用不同的内层地址；同机重复的 UDP 端口、已用槽位、管理地址覆盖及既有路由冲突都会被拒绝。界面建议仍须审阅，实际机器端口占用由远端预检确认。
5. 在前置「管理线路」选择中转与原落地节点，再在「实例间连接」选择“两段加密”。已有单段选择继续可用。
6. 设置本线路独立的前置／中转端口和前置来源。前置→中转使用通道时，中转白名单限定前置在该通道内的 `/32`，原公网前置出口字段禁用。
7. 核对两段方向、三台依赖、监听和白名单。取消审阅不创建任务或写入依赖；实际业务与两段新挑战全部通过才提交。
8. 到配置设计添加整条线路，生成、固定核心校验并导出。客户端连接前置端口，使用原落地连接身份。

每台两个槽位是长期的资源边界。原槽位继续使用自己的资源身份；新增第二槽位不重写原通道、密钥或依赖指纹。两个槽位均占用时仍可查看、检查、移除已有通道，不能通过新名称绕过限制。

## 多入口和多目标

独立 TCP 转发按纵向规则编辑，每条监听对应一个目标。可用“复制为另一入口／目标”保留目标、来源、验收方式和 PROXY 选择，再填写新端口；复制会生成新身份并清空监听端口，防止无意重复。

| 目的 | 配置方法 |
| --- | --- |
| 两个入口端口访问同一目标 | 建两条规则，分别填写不同监听端口；目标地址和端口可以相同。 |
| 同一实例提供两个不同落地 | 建两条规则或两条编排线路，分别选择来源、端口及落地；不要填写目标列表。 |
| 两个前置复用中转／落地 | 分别创建线路，中转规则必须用不同监听端口和准确的前置来源。 |
| 多条线路借用同一相邻通道 | 每条线路各自固定依赖摘要；删除一条不会解除其他线路的引用。 |

共享实例变更沿用[共享线路保护](SHARED-CHAINS-ROUND-25-2026-11-01.zh-CN.md)：锁定受影响实例、核对存续规则并实际复验相关业务。更新共享转发组件会重建其监听，既有连接可能短暂重连，审阅会明确提示。这里没有引入不中断更新的承诺。

## PROXY 输出和信任边界

普通转发默认不附加任何头。选择 PROXY 后，受管工作进程在应用数据之前发送一次头，地址取自该进程接受连接的内核 socket：

- v1 使用 TCP4／TCP6 文本地址与端口。
- v2 使用 TCP 地址字段，不声明 TLS 身份、用户、命令或扩展 TLV。
- 输入始终是应用数据，不识别、不接受客户端声称的 PROXY 来源。客户端发来的同名文本不会覆盖内核来源。
- 如果前面还经过别的转发器，输出的是本跳实际对端。没有接收与核验前一跳声明的功能，因此不能把它说成跨任意多跳保留最初客户端 IP。

目标必须配置为接收对应版本，并限定只信任本转发服务器。PROXY 自身不提供认证，目标也不能因此开放其他来源的身份声明。其语义按 [HAProxy 协议说明](https://www.haproxy.org/download/2.9/doc/proxy-protocol.txt)实现；普通 TLS 目标不支持头部时，TLS 证书握手验收失败，事务不会提交。

操作顺序：在独立 TCP 规则选择“发送 PROXY v1／v2”，填写明确目标及 TLS SNI，审阅后执行。TLS 继续校验证书和主机名，不增加跳过校验选项。该模式本轮不用于代理来源节点生成，也不在编排线路中自动打开。

Debian 12／13 的普通转发继续使用原 systemd-socket-proxyd。PROXY 使用单独的 socket 激活工作进程，以避免把新 systemd 才提供的参数写进旧系统；系统版本边界可核对 [systemd 文档](https://www.freedesktop.org/software/systemd/man/latest/systemd-socket-proxyd.html)。工作进程非 root，固定目标，无 Shell／动态 DNS／用户脚本，最多256连接、每方向64KiB用户态缓冲、连接建立5秒、连接空闲300秒、无连接60秒后退出，服务内存上限96MiB。它不增加一直运行的控制端服务；这些是运行边界，不代表测得全应用资源下降。

SSH 欢迎信息可能在目标处理输入前已经发送，不能证明 PROXY 头被接收。因此本轮不允许以 SSH 响应作为 PROXY 验收；普通 SSH 转发仍按原范围检查。

## 验收和恢复

双段线路在每次应用／检查时读取两个通道的实际配置、公开身份、接口和路由。每段都有本次双向 TCP／UDP 挑战，分别固定通道身份、方向和依赖摘要，再执行整链代理 HTTPS 与所需应用 UDP 回程。一个通道的成功、旧挑战或 TCP 成功都不能代替另一段及 UDP 证据。

| 异常或操作 | 行为 |
| --- | --- |
| 任一段漂移、移除或最近检查失败 | 旧线路客户端来源资格失效；不降级为公网。 |
| 新建／移除第二通道失败或取消 | 只按该槽位及本次防火墙快照补偿；已有第一通道保留。 |
| 另一槽位有待恢复事务 | 整台机器先统一恢复，不能用空闲槽位绕过事务归属。 |
| 线路操作失败 | 恢复本次转发与相关防火墙；不会重建、删除或恢复借用的两个通道。 |
| 远端确认丢失 | 按原任务身份查询状态并补偿，不重放变更。归属不明则保留恢复材料。 |
| 移除一条线路 | 保留通道及其他线路；还有活动／待恢复引用时不能删除通道。 |
| PROXY 应用验收失败 | 恢复旧规则、工作程序、单元及相应防火墙；错误 SNI 不会通过关闭 TLS 校验处理。 |
