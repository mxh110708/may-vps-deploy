# 第十一轮：转发节点接入配置设计与真实生命周期验证

本轮将已经应用的独立转发接入客户端配置设计。保留原有方案、双客户端生成、真实核心校验、审阅导出和组件事务；不增加常驻控制进程、监测计时器或自动同步任务。源码尚未发布，未安装用户应用或变更生产 VPS。

## 使用流程

1. 在实例的 TCP 转发中使用已保存代理节点作为目标，并完成代理验收。单纯 TLS／SSH 验收没有完整代理凭据，不能据此自动猜测节点。
2. 打开「配置设计 → 节点 → 添加转发节点」，选择具体规则、监听地址族及入口地区组。双栈规则分别显示 IPv4、IPv6 两个连接。
3. 核对显示的连接端点和 TCP／UDP 能力，再点击「添加／更新」。这一步只修改当前方案，不联系服务器，不修改原始节点或已导出的配置。
4. 使用正常的「生成配置 → 核心校验 → 审阅导出」。需要实际连接验证时，从连接页运行已有的可取消轻量诊断。
5. 调整转发后重新选择该来源更新节点。稳定身份、自定义名称、节点用途和分组保留；旧候选失效，不追加重复节点。

已有转发需要与当前配置匹配的验收记录。旧版没有记录配置摘要的规则，先执行「只读检查已保存转发」；发现旧启动单元时，再明确审阅保存规则更新单元。检查本身不改服务器。

## 参数与传输能力

- 复制目标的完整双客户端原生连接，只改客户端连接的服务器地址和端口；保留密码、UUID、Reality、TLS／ECH 及其他受支持参数。原配置依赖服务器地址作为 TLS 身份时，将该原身份显式保留，避免连接到转发地址后错误验证证书。
- Reality／AnyTLS 自带的 UDP 封装按原协议参数保留。TCP 字节转发本身不会把它们的封装流量变成独立 UDP 转发。
- Shadowsocks 没有匹配的独立 UDP 转发时，Mihomo 明确关闭 UDP，sing-box 限定 `network: tcp`。只有同实例、同监听端口、相同目标和来源、覆盖所选地址族且完成实际验收的 UDP 规则，才能组合为 TCP＋UDP 节点。
- 已有 TCP-only 节点不会仅因后来新增 UDP 规则而自动启用 UDP；重新添加／更新时显示新组合，确认后才修改当前方案。
- 不生成 UDP-only 的普通代理入口；目标含额外客户端上游、仅 UDP 参数或缺少完整双客户端配置时明确阻止。转发节点再次作为服务器下一跳或转发目标留待后续多跳设计，本轮不隐式组合。
- 编辑转发节点只修改显示名、用途及分组，不通过简单表单重建或泄露来源凭据。分享链接仍使用既有的完整参数能力检查；无法表达 TCP-only 或 ECH 等设置时阻止分享，完整配置导出继续可用。

## 来源、失效与保存

转发来源保存实例、规则 ID、监听地址族、规则摘要、可选 UDP 规则及连接摘要。目标参数仍来自已加密保存的原始方案。生成、核心校验、导出审阅、实际导出、分享和轻量诊断均复核来源；诊断结束再次核对，避免把来源已变化的结果记作当前结果。

实例处于部署／恢复中、规则停用或删除、监听地址／端口、允许来源、目标、凭据或绑定 UDP 变化时，旧引用不能继续导出。与该节点无关的规则名称、检查时间及未绑定的 UDP 规则不自动改变其身份。批量选择先在副本上处理，失败不会部分修改当前方案。

这些检查依据本地已纳管归档及最近验收证据，不声称打开方案时已经实时探测公网。实际诊断另行明确执行。

## 实际重启发现的修复

Debian 12 实机虚拟化测试发现，转发 socket 默认位于 `sockets.target` 之前，而其依赖的白名单 service 默认位于 `basic.target` 之后，形成开机 ordering cycle。日志显示 systemd 为打破环删除启动作业，重启后的监听状态可能与归档不同。

TCP 与 UDP 的白名单单元现明确使用 `DefaultDependencies=no`，位于 `sockets.target` 之前，并保留 nftables 的顺序及关机依赖。它们依然先建立来源限制，再允许监听启动。

单元模板更新沿用控制端已归档的完整资源摘要：只允许原摘要准确匹配的受管旧单元进入审阅更新，未知文件、额外单元、覆盖和外部改写仍拒绝。读取旧单元不自动改写；健康检查和只读检查提示重新保存。快照固定原文件和恢复程序，恢复按原摘要核验旧单元，不靠硬编码历史模板或放宽配置内容判断。
