# 监控快照新鲜度异常：隔离复现与修正验证

日期：2026-10-26。本文补充 [M5 长测最终报告](MONITOR-M4-M5-2026-10-25.zh-CN.md)，不替换原状态文件或 2882 行原始采样，也不将短测拼成新的 24 小时观测。

## 结论

已在隔离对照中确认一个真实的时间顺序缺陷：先记录快照捕获时间，再读取期间到达的新报告，新报告时间就可能晚于快照时间。严格检查 `0 ≤ 报告年龄 ≤ 15 秒` 时，会将该报告排除，产生“五台在线、只有四份新鲜”的结果。

生产现有 RC6 的快照逻辑已在收集报告完成后记录捕获时间。本次补充了能稳定触发旧顺序错误的回归，以及对该修正的实际二进制验证；没有为此再修改或重启生产服务。

原长测只保存了汇总，没有保留异常节点的完整报告，所以不能证明历史那一次必然只有这一原因。历史记录的 `NeedsReview` 保持不变；本次能够确认的是**同型缺陷可复现、当前修正有效，且后续诊断信息已补足**。

旧顺序对照是独立源码副本，只移除“组装结束记录捕获时间”这一行，保留其余代码和相同测试。它不是重跑原 RC4 完整长测，也没有替换任何冻结资产。

服务端回归位于 `server/securityaudit/read_integration_test.go`，由既有安全边界测试调用。该文件是测试，不进入生产二进制。

## 实际 RC6／RC3 二进制核验

本机独立回环服务启动一个 RC6 Server 和五个真实 RC3 Agent，使用临时数据和合成凭据，GeoIP、远程控制和自动更新关闭。等待五份报告都新鲜后，连续约 45 秒读取快照：

- 665 次快照均为五在线、五新鲜。
- 未出现负报告年龄，最小观测年龄为 0.000616 秒。
- 结束后自有 Server 和五个 Agent 全部退出。

这是针对时间边界的真实进程短测，不是第二次 24 小时可靠性或资源基准，也不验证公网业务吞吐。生产主机、CF、Tunnel、代理及 SSH 均未修改。

## 后续采样诊断修正

以前只保留在线数、新鲜数和最大年龄，无法从“五／四”反查是哪项条件失败。`tests/observe_may_monitor.py` 现在补充：

- 快照捕获时间、带符号的最小／最大报告年龄和分类原因计数。
- 异常时保存各预期节点的槽位、上报时间、年龄、在线状态及限定的七项指标；正常采样不写逐节点详情。
- 区分报告来自未来、报告过期、无报告、时间格式错误、无指标、指标无效、离线、缺失节点和重复节点。读取失败只记错误类别，不记录凭据或响应正文。
