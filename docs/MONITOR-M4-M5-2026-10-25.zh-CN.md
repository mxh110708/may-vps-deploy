## M4：修改 Agent 地址与凭据

从 Deploy「监测 → 部署与维护」选择明确的实例、Agent 组件和「修改 Agent 地址与凭据」。

1. 先核对该 Agent 的实际安装、文件摘要、专用服务及进程。组件须已安装、启用且运行；已停用的组件先显式启用。其他组件待恢复时不能借本操作绕过恢复。
2. 填入新的 HTTPS 地址，保留原 May 节点 UUID，并填写预期 Server 安装身份。身份应从受管 Server 的核对结果取得，不能把显示名称或相同版本号当作身份。
3. 默认保留原 Token。只有勾选替换后才在执行阶段要求输入新 Token；不在公开操作参数、URL、普通日志或任务摘要中存放 Token。只读令牌不能用于 Agent。
4. 通过正常 TLS 向新端点发送节点凭据检查。禁止跳过证书检查、跟随重定向或使用公开 HTTP；只有本机回环测试允许 HTTP。返回值必须匹配原节点与填写的 Server 身份。
5. 核验失败发生在备份事务和服务重启前。相同地址且保留 Token 时不制造无效重启；保留模式还核对控制端归档凭据与实际配置，避免把过时归档继续标成已同步。
6. 核验通过后先做同组件一致性备份，再仅修改地址／Token。保留二进制版本、节点身份、采样参数、TLS 策略，以及关闭远程控制和自动更新的设置。
7. 重启所选 Agent 后，最多等待约 35 秒。至少读取三次新鲜有效的状态、至少出现两个不同的真实报告时间，且时间不能倒退。首条报告暂缺会继续等待，不能当作异常或用零值代替。
8. 验收通过才加密归档新凭据并提交。Server 的凭据检查只返回当前认证节点的身份与时间，不返回主机指标，也不会刷新在线租约或创建节点。

接口检查证明的是已有 Token 的身份，不为本功能保存长期管理员 API Key，也不自动创建或移动生产节点。

### 撤销旧 Token 后的恢复

准备轮换时先在 May 管理端为原节点设置有效的新 Token，然后在 Deploy 显式输入。旧 Token 即使已撤销，也允许使用新 Token 对原节点完成修改；不会要求先用失效 Token 登录。

若应用或验收失败，事务先尝试恢复同组件快照。只有原连接恢复真实上报后才标记回退成功。旧 Token 已撤销时，恢复旧文件不能恢复连接：

- 远端保留 `CredentialRecoveryRequired`，本机仍为需要恢复，不释放成“已完成”。
- 停止该事务的自动回退定时器，避免持续重试失效凭据。
- 在同实例 Agent 的「恢复 Agent 连接（待恢复事务）」中明确输入原节点的新地址、Server 身份和新 Token。
- 修复沿用原事务，重新核对实际状态摘要、节点、服务身份和新上报，成功后提交并同步加密归档。
- 修复回复丢失时只查询事务。确认已提交可以收敛；其他情况保留需要恢复，不能自动重放修复、重复提交或改用其他组件的恢复。

服务端维护检查、Agent 新连接、原连接恢复是三个独立步骤。没有通过连续上报验收就不能声称已经恢复。

## M4：只读授权续期与撤销

先在本机保存只读连接及明确的实例／节点 UUID 绑定，再选择受管 Server：

- 「应用／续期本机只读授权」允许 1–90 天，默认 30 天。服务端只接收 Token 摘要、节点范围及到期时间；原始只读 Token 留在控制端。
- 可以续期同一 Token，也可先在本机生成新 Token 后应用。每个 Server 当前维护一份此类授权，不借续期扩展成管理员访问。
- 应用会重启选定 Server，因此审阅中明确显示这一影响。之后必须从控制端通过正常 HTTPS 读取，核对当前连接、Server 安装身份、授权范围与响应时间，才提交。网络错误、身份或来源变化会恢复原授权。
- 「撤销服务端只读授权」删除该 Server 的授权文件及归档中的授权摘要，并重启服务；不删除节点、Agent Token、本机连接或监控数据。实际服务验收已确认原只读 Token 返回 401。
- 维护页面区分未配置／已撤销、已过期、七天内到期及有效至指定时间。旧归档没有到期信息时显示未配置或需核对，不推定仍有效。

授权状态是最近核对的配置结果；HTTPS 检查失败、Server 离线及 Token 过期不得统一显示为节点正常离线。

## M5：保留的修改与证据

### 近期报告缓存

以前每次上报都为该节点整个近期窗口重新分配切片并复制。现在复用受锁保护的缓冲，只在需要扩容时分配，清理过期条目时清除尾部引用。返回给外部读取者的切片仍复制，不能通过读取结果改动缓存。

兼容端点的缓存保留最近一分钟、最多 128 条报告。默认三秒上报和一秒上报均有余量；自定义高频／突发报告超过上限时只保留最近 128 条。这个上限不修改 Agent 采样频率，也不替代或截断独立的持久化指标历史。

同机三次 `BenchmarkReportWindowUpdate`，模拟稳定的 20 条窗口：

| 状态 | 每次操作分配量 | 每次操作耗时 |
| --- | --- | --- |
| 修改前 | 15,616 B | 1,747–1,792 ns |
| 修改后 | 约 539 B | 204–209 ns |

这证明该路径的分配和执行开销下降，不能据此宣称整个 Server 的常驻内存下降相同比例。整进程收益留给单／多节点长测判断。

### Agent 网络统计

原实现的采集协程读取全局定时器和停止通道。重配／启停交错时，旧协程可能进入新一代通道，且启动标记和只读初始化存在数据竞争。现在每代协程固定自己的通道，拿锁后再次核对代次及运行状态；启动检查进入锁内，读取函数不再持读锁初始化共享状态。

将同一个并发启停、配置与读取测试放到原提交的临时源码副本，真实复现 `DATA RACE`；当前源码连续三次竞争检测通过，没有遗留工作协程。保留现有采样频率和流量计算，计数器回退仍记为零增量，不制造巨额虚假流量。

非有限、负数或无法转换为有效定时器／保留时长的值在生效前拒绝。保留期清理改在写盘前完成，保存失败向调用者返回错误。月流量历史在启停后仍保留有效记录。

### 持续存储错误的背压

通过 SQLite 实际 `SQLITE_FULL` 错误检查了失败路径，未填满用户磁盘。首次失败的待写汇总保留，可在存储恢复后重试；失败不能变成正常的零值样本。

补充验证发现，持续失败后原实现仍可能接收新样本并增加内存汇总。现在记录失败的刷新边界：后续写入先重试该边界之前的待写内容，失败就明确拒绝新增写入，避免把内存当成不断增长的备用数据库；正常写入只有空状态分支，没有新增轮询或定时器。

测试连续二十次新增写入均被拒绝、原样本数保持不变。解除页数限制后旧数据完整落盘、可继续接收新数据，无重复计数或补零。保留在内存中的未落盘数据不等于持久化，容量不足时强制重启仍不能保证找回这些样本。

### 已有行为的审计结论

- 原始指标窗口、压缩／降采样、配置保留期、分钟／五分钟／小时层级、过期清理和旧样本查询已有实现；本轮验证这些行为，没有重新增加第二套历史库或高频清理器。
- SQLite 保持单写连接和两个只读连接，不通过增加写并发掩盖磁盘错误。
- Agent 断线重连、HTTP／WS 存在状态交接与旧连接的条件删除已有回归；真实 VM 另行验证了 Server 重启后重新报告。
- Deploy 只在监测页按需要读取，默认不启动自动刷新；离开、隐藏或关闭会停止定时器、取消读取并释放客户端。过期显示由一次性到期事件处理，不额外发网络请求。保留这些行为，没有让 Deploy 持续 SSH 轮询。

## Web 与 Deploy 的短时资源基线

这些是建立口径的短测，不作为长期内存优化结论，也不将主机内存指标当作应用进程内存。Web 前端没有在本轮修改；Web 测量使用新增磁盘背压前的 M5 候选，正常浏览流程一致，仍保留该准确边界。

独立无头 Edge 进程树合计，包含浏览器本身、渲染器和 GPU。各阶段约 12–24 秒；概览包含初始加载开销，不能视为稳定空闲 CPU。CPU 按单个核心的百分比计算，不能直接与任务管理器整机百分比比较：

| 阶段 | 私有驻留内存中位数 | JS 堆中位数 | 单核 CPU 中位数 |
| --- | --- | --- | --- |
| 初始概览 | 346.24 MiB | 7.61 MiB | 16.18% |
| 节点图表 | 300.84 MiB | 16.81 MiB | 1.54% |
| 切到空白页面 | 289.64 MiB | 0.42 MiB | 1.54% |

浏览器和测试服务最后全部关闭。该短测不能证明前台浏览器常驻占用已优化；M7 的普通浏览器体验和持续图表场景仍需单独验证，不能把浏览器共用进程全部计给一个页面。

Deploy 使用真正的 WinUI EXE 和屏幕外合成会话；没有修改用户安装。概览空闲 18 秒、完成监测读取并离页后 30 秒：

| 阶段 | 工作集内存中位数 | 私有提交量中位数 | 单核 CPU 中位数 |
| --- | --- | --- | --- |
| 概览空闲 | 143.13 MiB | 101.16 MiB | 0% |

短测显示停止读取后 CPU 可以回到空闲，但窗口控件和运行时缓存仍留有内存；本轮没有强制 GC、周期裁剪工作集或声称已经降低整个 Deploy 的驻留内存。屏幕外测试不包含正常前台合成器／GPU 的全部成本。测试进程已退出，停止后不保留桌面采集者。
