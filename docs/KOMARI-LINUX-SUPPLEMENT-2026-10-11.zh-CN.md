# Komari 旧备份 Linux 隔离补测

> 文档定位：旧归档／Komari 实施记录，保留当时的判断与验证范围；不是当前 May Monitor 迁移或安装教程。当前使用见[监控运维](MONITOR-OPERATIONS.zh-CN.md)和[维护手册](MAINTENANCE.zh-CN.md)。


2026 年 10 月 11 日，在用户明确授权后，将两份真实备份的一致性数据库副本上传到 VMISS 专用测试机，完成 Linux amd64 后端的恢复、版本兼容和重启验证。本轮补充 [v0.9.14 测试记录](TESTING-0.9.14.zh-CN.md)，没有修改应用代码、重打安装包或替换已发布附件。

## 材料与隔离范围

- 两份备份均包含 SQLite 主库、独立 MetricStore 及配套 WAL/SHM。先用 SQLite 备份接口生成一致性副本，上传前后核对副本摘要；两份原始压缩归档的摘要不变。
- 较早备份内旧程序对应官方 Komari 1.4.3。旧 Linux 程序核对官方发行摘要；新程序对应项目固定的 Komari 1.5.1，并核对固定摘要及版本 API。含历史备份缺少可核实的旧程序版本，所以该份只验证新版恢复与重启，不推断其原版本。
- 每轮使用带所有者标记的独立私有目录及临时 systemd 服务。服务使用独立网络命名空间，只能访问自己的回环接口；主机系统路径只读，只允许写入本轮目录，并禁用提权。实际检查命名空间、挂载权限和服务属性，不能连接原节点或发送通知。
- 仅调整测试副本的数据库路径、临时 API 凭据、通知和任务设置、历史保留参数。后台测试没有使用全局鼠标/键盘、切换代理或 TUN，也没有修改非测试 VPS。

## 结果

| 项目 | 结果 |
|---|---|
| 较早备份 | 官方 Linux 1.4.3 启动并读取副本，停止后改为官方 Linux 1.5.1；版本 API 与构建标识一致 |
| 含历史备份 | 1.5.1 实际启动后，节点 API 返回原有 5 个节点 |
| 账户与设置 | 两份副本的账户、节点及未调整的原有配置、主题配置内容摘要一致；允许新版添加默认项及版本元数据 |
| 指标历史 | 100 个指标序列与全部 132,900 条汇总记录保留；按原有列排序计算内容摘要，新版启动、后台处理及重启后相同 |
| 数据完整性 | 两份副本的主库、指标库均通过 SQLite 完整性检查 |
| 服务重启 | 两个新版临时服务均执行实际重启，进程标识变化，版本与节点 API 再次就绪；随后停止服务再核对数据库 |
| 现有部署 | SSH、受管文件与配置摘要不变；现有代理、主控、Agent、Tunnel 的状态与进程标识不变；账户及管理配置摘要不变 |
| 清理 | 本轮临时服务已停止，本轮目录及上传副本已删除，没有残留本轮子进程；原始备份再次核对摘要不变 |

## 修正测试参数后的复测

一次复测发现历史副本的汇总记录从 132,900 条降为 63,600 条。诊断确认减少的 69,300 条来自两个粗粒度汇总层级；其余账户、节点、设置及序列保留。这次尝试记录为失败并清理，没有计为通过。

原因是测试副本把三个分层保留窗口全部设成相同的长期值，却仍保留原指标的 15 天期限。固定新版会按单项指标期限限制层级，并删除不再延长保留期的粗层级；规则见 [官方固定版本的分层策略](https://github.com/komari-monitor/komari/blob/f0cc0fba38ce161935372633cae5248c934e2b23/pkg/metric/rollup.go)。这是本轮测试参数的错误，不能据此判定应用升级丢失数据，也不能只用版本 API 就绪判断历史保留通过。

复测重新从未修改的一致性副本开始，只将测试副本的分钟、五分钟、小时窗口设为逐层递增的期限，同时延长单项指标期限，使各层均覆盖备份时间。启动与重启后留出后台处理时间，停止服务后再次核对完整性、记录数与内容摘要，全部通过。未改动历史行内容或时间戳，也没有放宽记录比对条件。此参数只用于核对旧快照的数据兼容，不是给正式主控推荐的数据保留策略。

## 仍未覆盖

- 两份备份均已采用独立 MetricStore，没有找到更老的单库历史或对应程序；旧单库到 MetricStore 的历史重构迁移仍缺少真实材料。
- 本轮在临时服务中执行后端版本替换，没有通过应用升级现有正式主控，也没有接入真实通知或原节点上报。
- 本轮属于备份兼容与重启验证，不等于长期留存、跨数据库后端迁移或完整历史重构验证。敏感备份、原始日志和数据库内容仅保留在本地私人测试证据中。
