# 组件版本维护

基线：Deploy v0.9.38。应用自身更新、代理核心、May Monitor、Tunnel、内核和客户端文件有不同版本与恢复范围。先读[维护手册](MAINTENANCE.zh-CN.md)，再选择具体组件。

## 来源与对象

| 对象 | 版本来源与边界 |
| --- | --- |
| 传统 Reality／AnyTLS／SS 服务核心 | 默认应用固定版；支持的入口可在审阅前查询对应官方最新稳定版，并把具体资产锁定。 |
| 通用多入站固定核心 | 使用当前包内固定来源；显式任务列出全部引用者，同版本不重复更新。 |
| May Monitor Server／Agent | 使用 `config/may-monitor.json` 固定的 May 资产、版本、字节数和 SHA-256，通过独立生命周期维护；不替换为 Komari latest。 |
| May Status | 固定 ZIP 与锁修订，静态资源暂存后经 Server 生命周期切换。 |
| cloudflared | 在对应 Tunnel 对象维护，程序更新与 Token 轮换分开。 |
| Google BBR v3 | 仅随应用提供的固定预构建内核与对应源码材料；不是 Google 官方二进制，也不查询浮动最新提交。 |
| 上游 Komari 组件 | 源码仍有独立的旧组件维护路径；它不等同于 May Monitor。已完成 May 迁移的实例不应走该路径。 |

代理核心的最新稳定查询只解析指定官方仓库，排除草稿和预发行；审阅显示版本、资产和可验证摘要，执行期间不重新浮动解析。查询失败不默默换来源。查询材料有效期、来源变动和归档漂移均须按实际任务核对。

新部署草稿锁定本轮版本和候选材料；继续同一草稿不因应用清单后来变化而偷换程序。接入已有 VPS 保留当前程序，升级从维护入口单独审阅。

## 升级步骤

1. 核对实例身份、当前版本、启停状态、配置和待处理事务。
2. 选择对象和来源，查询适用候选，审阅具体版本、架构、URL、大小、SHA-256 和影响范围。
3. 做同组件一致性快照，校验完整新资产与归档成员后应用。
4. 验证实际程序、原配置和启停状态，再做对应协议／HTTPS／Agent 新报告验收。
5. 本地归档与远端一致后提交；确认丢失先只读核对同一事务。

核心更新保留原端口、配置与凭据，不借升级轮换 Token 或更换端点。共享核心更新列出实际影响的入站和用户。版本未升高不能伪装成新升级；明确重新安装也要走对应受管流程。

May Server 备份、Agent 配置、静态主题、读取授权与外部 Tunnel 分别管理，详见[监控运维](MONITOR-OPERATIONS.zh-CN.md)。旧 Token 已撤销时不能用旧文件恢复认证。未写入的升级恢复不应覆盖已经继续增长的监测历史。

BBR 安装与重启只在[网络调优](NETWORK-TUNING.zh-CN.md)明确审阅后进行，保留恢复内核；Windows 附带 .NET／WinUI／Python／校验核心则随应用整体维护。选择来源不隐式安装、重启或改动客户端权威文件。
