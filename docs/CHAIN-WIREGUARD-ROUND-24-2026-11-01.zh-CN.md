# 第二十四轮：WireGuard 接入跨实例线路编排

日期：2026-11-01。本轮在源码中把第二十二轮已验收的双实例 WireGuard 通道接入第二十一轮三实例编排。本轮随 v0.9.40 发行；隔离验收不代表已安装或应用到生产。单独的 WireGuard 管理和不选隧道的原生线路继续可用。

## 能解决什么

后续[追加功能](SHARED-CHAINS-ROUND-25-2026-11-01.zh-CN.md)扩展了共享实例的多线路管理，此前误标第25轮，现已纠正。下文「每台实例一条线路」为第二十四轮当时范围；追加功能保留单台一个 WireGuard 通道／单线路一个加密段的限制，验收不倒写至本轮。

已有的前置→中转→落地线路，现在可以明确选择其中一段通过两台实例之间的 WireGuard 内核通道转发。另一段保持原生连接，客户端仍连接原前置端口，落地仍使用原协议、用户、证书、SNI 和出口。

| 选择 | 前置→中转 | 中转→落地 | 需要预先完成的通道 |
| --- | --- | --- | --- |
| 原生直连 | 原地址族 | 原地址族 | 无 |
| 前置→中转 WireGuard | 对端隧道内 IPv4 | 原地址族 | 前置与中转之间的已验收通道 |
| 中转→落地 WireGuard | 原地址族 | 对端隧道内 IPv4 | 中转与落地之间的已验收通道 |

原生连接与客户端入口可选 IPv4 或 IPv6；WireGuard 外层 IPv4／IPv6 独立于该选择，内层仍为两端 IPv4 `/32` 主机地址。选择 IPv6 入口不代表 WireGuard 内层也是 IPv6。审阅分别展示实际监听地址族和加密段。

本轮保持每台实例一个 WireGuard 通道、一条活动编排线路的限制。因此一条三实例线路只选一个相邻通道，不同时创建两个共享中转的 WireGuard 对，也不扩展任意深度拓扑、默认路由 VPN、DNS 或 NAT 管理。

## 使用前准备

1. 三台不同的受管 Debian 12／13 amd64 实例具有有效 SSH 身份、可用管理连接和完整私人归档。先解决其他未完成事务。
2. 在实例页「管理隧道」完成所选相邻两台的部署及双向 TCP／UDP 验收。隧道必须处于活动状态，最近检查不能失败，两端配置、密钥公有身份及远端资源摘要必须与归档一致。具体防火墙、外层端点、MTU、保活和恢复流程见[第二十二轮](WIREGUARD-ROUND-22-2026-10-30.zh-CN.md)。
3. 保存已验收的原落地来源节点。TCP 沿用原三实例编排所支持的来源；UDP 仍只支持固定端口 Hysteria2／TUIC v5，不支持任意 UDP、端口跳跃或把 TCP 节点伪装成 UDP 节点。
4. 落地服务必须监听实际连接地址。选择中转→落地通道时，落地须能从自己的隧道内 IPv4 接收所选协议。仅绑定公网 IPv6 的监听不能因为入口选择 IPv6 就自动接收隧道内 IPv4；调整独立入站须另行审阅、验收并刷新来源节点，本轮不会替你扩大监听。
5. 前置白名单仍限定实际客户端／控制端来源。选择前置→中转通道时，中转规则只允许前置的隧道内 `/32`；未使用的公网前置出口字段在界面禁用。选择中转→落地通道时，中转仍按前置的原生真实出口 `/32` 或 `/128` 限制来源。

WireGuard 通道只适合相互信任的受管实例。其既有防火墙允许对端访问本机已有监听服务的范围保持第二十二轮语义；选择编排不会收窄或扩大该独立通道的信任范围。服务商防火墙与「保留既有防火墙」模式下的外部规则仍需自行准备。

## 创建、审阅与使用

1. 从前置实例打开「跨实例线路编排 → 管理线路 → 新建线路」。选择地址族、转发传输、中转及原落地节点。
2. 在「实例间连接」选择原生直连，或对应相邻两台的已验收 WireGuard。列表显示加密方向、通道名称及外层地址族，不提供不相邻或尚未通过验收的通道。
3. 填写前置／中转端口及前置允许来源。换中转、落地或地址族／传输后重新选择通道，避免沿用旧拓扑。保留的通道选择如果已变化，会明确显示不可用，不能静默当作原生连接提交。
4. 审阅三台依赖、实际地址族、传输、端口、白名单、加密方向和恢复范围。摘要不包含私钥、密码或完整代理身份。取消审阅不产生远端任务或线路依赖。
5. 执行到完整线路验收与提交完成。成功后在配置设计「添加转发节点」选择整条线路，生成、校验后导出。

隧道不会因为线路使用它就被重新部署。改变加密段、通道身份或拓扑时，先移除旧线路，再以新身份新建并验收；不是手改活动归档。

## 执行时如何判定通过

复用独立 WireGuard 的业务证明实现，没有增加常驻探测器。每次新建／检查按本次请求重新验证：

1. 固定三台计划、状态、来源方案、线路及通道记录、相关程序摘要，按原三台锁顺序复核审阅。通道摘要涵盖双端配置、公开密钥身份和远端资源摘要，普通检查时间变化不改变该身份。
2. 核对全部机器、管理路径、落地身份和转发资源；读取两端实际 WireGuard 配置、路由与运行状态，和归档逐项比较。写入前就发现漂移时停止，不尝试修补或替换隧道。
3. 沿用已有转发事务：先中转后前置，仅写所选 TCP／UDP 规则及其受管防火墙范围。
4. 两个方向分别执行本次随机挑战的 TCP 和 UDP 往返，核对回应、方向及挑战摘要。不能用旧握手时间、单方向成功、旧挑战结果或 TCP 成功代替 UDP。
5. 再读取通道，完成两段 TCP 连接／UDP 路由记录和原代理协议、HTTPS 整链验收。QUIC 还必须完成真实应用 UDP 回程；路由可用不等于业务可用。
6. 提交前再次复核通道、转发、落地和管理连接。验收期间漂移、取消、认证失败或回程缺失均不提交，并按本任务快照补偿。没有回退到公网连接的分支。

临时挑战接收器在成功、失败与取消后都按自己的挑战身份清理。线路证据包含本次双方向证明及固定依赖摘要，原通道记录和整链业务证据各自保留用途。

## 检查、移除与恢复

| 情况 | 正确操作与范围 |
| --- | --- |
| 希望检查活动线路 | 在线路页执行「只读检查整条线路」，重新核对通道和整链业务；不重建隧道。 |
| 最近通道检查失败 | 旧线路候选、节点组复用后的生成／导出继续经过来源检查并被拒绝；先在隧道页解决问题并重新检查，再检查线路。不会仅因检查失败就自动拆除活动业务。 |
| 通道配置／公开密钥身份／资源摘要变化 | 原线路所固定的依赖失效；不能仅靠改时间戳或重新生成客户端绕过。核对后移除旧线路，重新选择并验收。 |
| 线路失败或用户取消 | 仅补偿本次前置、中转的转发和相应防火墙。落地协议、WireGuard 服务、私钥、路由及其他组件不属于线路恢复范围。 |
| 远端提交确认丢失 | 按原任务身份读取实际事务；部分实例已提交仍按同一快照补偿，不自动重放应用命令。 |
| 远端不可达、其他任务归属或补偿未完成 | 保留待恢复记录和依赖，从线路统一恢复入口继续，不删除事务文件绕过保护。 |
| 不再使用线路，但保留通道 | 移除线路成功后解除三台线路依赖，通道仍在且可独立检查；最近健康检查失败或独立通道摘要已变化不阻止按归属移除转发，不覆盖变化后的通道。 |
| 同时退役线路和通道 | 先完整移除／恢复线路，再单独审阅移除通道。活动或待恢复线路仍引用通道时，通道移除被拒绝。 |

生成、校验、分享和导出沿用已有统一来源核对路径。删除线路、通道已知失败或双端身份变化会使旧来源资格失效；检查并非持续网络监控，未执行检查时不能声称已经检测到所有远端变化。

未选择 WireGuard 的旧 schema 1 记录继续按原语义读取，不加默认字段、不迁移指纹、不修改旧凭据。加密通道作为可选依赖进入新线路配置；没有为改名迁移增加临时兼容分支。

## 验证记录

最终模型与故障专项通过 1,138 项断言：两个加密段、双地址族、TCP／两种 QUIC、方向反置的归档、非法引用、审阅后变更、双端摘要漂移、旧挑战、缺少 UDP、取消、确认丢失、部分提交、补偿失败与续做、通道故障／摘要变化时移除保留通道及来源失效。旧第二十一轮 498 项、独立 WireGuard 238 项专项也通过。相关 `chains` 回归组通过 2,033 项，包含本轮与既有转发、入站和通道用例；独立 Reality 的真实 Xray 配置检查因缺少 `MAY_TEST_XRAY` 明确跳过，模型与事务检查照常执行，不把它计作已执行。

最终 WinUI 使用已有后台接口 `suite.tcp-chain` 通过，覆盖通道选择、禁用未使用字段、已选通道失败时停留表单并显示错误、草稿、审阅、取消、已有线路、恢复及进度；窗口激活 0、前台采样 0、生产连接 0，测试应用已关闭。新增界面断言曾错误要求中文错误必须包含英文 `WireGuard`，修正为实际行为判断后通过，没有改变产品拒绝规则。Core／测试及 WinUI 最终构建均为零警告、零错误。

主校验 `ValidateProject` 通过，其主入口为 995 项断言，另包含交互、工作台、GUI／更新与可执行 Python／Bash 检查；受平台限制的项目按日志明确跳过。676 份公开文本秘密扫描及改动夹具的 Python 编译检查通过。主校验与 .NET 专项分别报告，不当作同一个断言总数相加。

前置→中转 WireGuard 的全新三机矩阵通过 95 项真实断言：IPv4／IPv6 各自的 SS2022 TCP、Hysteria2 和 TUIC v5，共六条路径，包含源入站验收、通道挑战、整链 HTTPS／所需应用 UDP、双客户端候选校验、只读检查、移除保留通道及最后一例真实提交确认丢失的补偿。

中转→落地最终全新三机矩阵通过 101 项真实断言，同样覆盖六条路径及真实提交确认丢失；双栈落地逐例通过正式维护流程清理自己的测试入站。两段合计 12 条实际路径、196 项断言，两段分别验证了一次真实提交确认丢失的补偿。

两段结果文件均逐项核对了六个地址族／协议组合、两方向匹配挑战、整链业务、所需应用 UDP、双客户端候选、移除清理和确认丢失次数。前置 Debian 12、中转／落地 Debian 13，客体间仍为独立 socket 网络，控制端经受限回环 SSH／有界数据报测试通道进入前置；这不是公网入站或 WAN 性能证明。

以下未通过的准备／夹具运行保留边界：

- 初次第二段复用了第一段保留的活动落地进程，固定核心复制收到 `Text file busy`，在准备阶段退出；改用全新三机。
- 一次全新夹具在 Debian 软件源索引下载时达到 180 秒准备超时，自动关闭；后续仅在测试机禁用不需要的源码／翻译索引，继续限定总启动时间。
- 另一次第二段矩阵完成 IPv4 TCP 后，下一用例新建的双栈入站与上一用例活动监听冲突，产品端口预检正确拒绝。修正为每例结束后通过正式入站维护流程移除自己的测试监听，再在新三机重测；没有放宽产品端口保护。
- 随后六条正常路径完成，但最后注入真实提交确认丢失时达到整组 9 分钟测试预算，取消发生在提交之前，预期的丢失确认断言未满足。该次整组未计为通过。中转→落地的双栈源会逐例验证两个地址族，因此把该整组测试预算明确设为 12 分钟、外层限制 750 秒，并逐例保存 `InProgress` 证据；仅完整结束才写 `Passed`。前置→中转仍为 9 分钟，产品单步超时、取消与故障阈值没有改变。

这些失败不计入通过，没有覆盖活动核心、调整产品超时或用路由检查代替业务。完成后核对五组夹具的自有 QEMU／SSH／监督进程均为 0，Windows 原生应用及客户端测试进程也为 0。结果、失败日志及最终后台界面证据保留在本机临时验收记录中，临时磁盘与测试密钥清理；没有停止 WSL 或其他任务的进程。
