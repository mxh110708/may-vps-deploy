# 第42轮：可信 PROXY 接收与端到端客户端 IP

日期：2026-11-25。本轮承接[第41轮](FORWARD-MULTI-TARGET-ROUND-41-2026-11-24.zh-CN.md)，为独立 TCP 转发增加显式启用的 PROXY v1／v2 接收、客户端网段核对及原来源透传。工作区源码与隔离验收完成，尚未提交、推送、发行、安装或应用到生产。第39–41轮的未发行改动保留，发行教程仍以 v0.9.42 为基线。

## 入口与配置

在实例的「独立 TCP 端口转发」中填写原有监听、固定目标和实际连接来源白名单。目标必须支持在 TLS 之前接收 PROXY 头；选择发送 v1 或 v2，保留 TLS 域名与证书验收。再显式启用「仅接收可信中转发送的 PROXY 头」，填写下表内容：

| 字段 | 作用与约束 |
| --- | --- |
| 接收格式 | 仅 v1、仅 v2，或 Auto 自动识别；均要求完整头部，不提供无头直连的自动回退。 |
| 可信中转 | 1–32 个规范 IP／CIDR，核对内核 socket 的实际连接来源。须被原有连接来源白名单覆盖，禁止全网 `/0`，不会自动加入此电脑。 |
| 允许声明的客户端 | 1–32 个 IP／CIDR，核对已信任中转声明的原客户端地址。可明确授权相应地址族的 `/0`；它与中转白名单是两层独立约束。 |
| 验收测试客户端 IP | 明确声明的测试来源，须属于允许客户端网段，不自动推断 NAT 之后的真实公网 IP。 |
| 验收原目的 IP | 与测试客户端同一地址族的明确单播地址，默认草稿取实例 IPv4。它只是验收元数据，不改变固定转发目标。 |
| 头部总接收时限 | 1–10 秒，默认草稿为 3 秒；从接受连接开始使用单调时钟，收到新分片不会延长期限，解析完成后再次核对期限。 |

启用后仍使用原来的配置版本 1，在规则中显式增加版本 1 的 `ProxyReceive` 对象。对象包含 `Version`、`Protocol`、`TrustedSources`、`ClientSources`、`ProbeSource`、`ProbeDestination`、`TimeoutSeconds`，不接受未知字段。旧规则没有该对象，不会自动迁移或信任输入。复制规则更换规则身份，保留接收策略草稿；关闭后重新开启保留本次编辑内容。

保存前的审阅列出可信对端、可声明的客户端范围、接收格式、总时限、测试端点及继续发送的版本。此电脑须在可信中转范围内，才能直接完成控制端入口验收；双栈入口须按实际出站来源放行两种传输。本轮不新增从任意远程主机执行验收的入口。

## 接收、发送与信任边界

接收顺序为：实际对端属于可信中转 → 完整头部通过格式与期限检查 → 声明客户端属于允许网段 → 分配固定目标或健康目标 → 重新生成一次输出头部。前三步未完成时，不创建下游 socket，也不推进轮询／哈希分配。

- 支持带地址的 v1 `TCP4`／`TCP6` 与 v2 `PROXY` 命令、INET／INET6、STREAM；拒绝 UNKNOWN、LOCAL、UNIX、UDP、TLV、超长头、无效端口、组播、未指定地址、映射 IPv6 与作用域声明。
- 支持分片及头部后紧随的业务数据；只消费本次输入头，保留其后全部应用字节。v1／v2 输出可独立选择，保留已核对的原来源／目的 IP 与端口，声明目的不决定实际转发去向。
- 只有发送而没有接收策略时，仍使用内核 socket 来源；输入中的 `PROXY` 字样仍是应用数据。普通转发和 UDP 转发不获得隐式头部解释。
- PROXY 不提供密码学来源认证。可信中转仍能在已授权客户端范围内声明地址；须从网络层限定中转，并保留下游服务自身的鉴权。收到来源头不等于完成最终用户认证。
- 下游只应信任当前转发端或封闭回环路径，不能因本轮功能而公开允许任何客户端向目标注入来源头。非可信对端即使发送格式正确、声明在允许网段内，也会被接收端拒绝。

格式和信任原则参照 [HAProxy PROXY protocol 规范](https://www.haproxy.org/download/2.9/doc/proxy-protocol.txt)。本轮实现的是上述明确子集，不宣称支持规范中的全部命令与 TLV。

## 多目标、健康与会话

接收可与原单目标、显式主备、轮询及来源 IP 哈希组合。只有完成可信接收核对后，TCP 来源哈希才改用声明的原客户端 IP；相同中转后的不同客户端可以分散到不同目标。旧规则、UDP 和未启用接收的 TCP 继续使用 socket 来源。

健康检查直接探测每个目标，保留证书及主机名校验。启用接收的规则使用已审阅的测试来源和原目的端点生成健康头，与控制端入口的合成验收端点一致；健康与状态读取不推进轮询游标。全部目标不可用时拒绝新分配，不回退到直连。已有 TCP／TLS 连接固定在原目标，不迁移、重连或重放。

保留每规则最多 256 个 TCP 连接、每方向 64 KiB 缓冲、5 秒下游建连期限与原空闲退出行为。未完成头部的连接也计入容量，满额拒绝新连接并保留已有连接。接收阶段仅缓存有界分片；v1 头至多 108 字节，v2 仅接受固定 28／52 字节的 TCP 地址头。

## 目标支持与证据口径

目标必须事先正确配置为支持 PROXY 的 TLS 服务；本轮不会自动改写现有代理入站，也不会把必须先发送头部的监听导出成可直接连接的普通客户端节点。

固定 Xray 26.3.27 的 VLESS／TLS／TCP 入站以 `tcpSettings.acceptProxyProtocol` 完成真实业务验证：两跳 v1／v2 转换、IPv4／IPv6 原客户端、VLESS UUID 鉴权和受控 HTTP 请求均通过，Xray 访问记录保留原客户端 IP 与端口。这里的 HTTP 请求运行于已验证的 VLESS/TLS 传输中，不把它记作内层网站 HTTPS 验收。测试目标限定回环，不修改系统服务或全局信任。

sing-box 的旧 `proxy_protocol` 接收字段已被移除，不能给当前固定核心直接开启该选项；普通 TLS／SSH 目标也不能因端口开放而算作支持来源头。目标自身是否继续使用来源信息执行业务授权，仍取决于对应服务的配置。

控制端证据范围明确记为 `ControllerDeclaredSourceTls`，包含当前完整规则摘要、实际发送格式及声明测试端点，并要求 TLS 证书通过。修改信任范围、客户端范围、测试地址、目标或策略使旧证据失效。这一证据证明本次声明头与证书握手路径，不冒充目标日志里的真实最终用户观测；端到端原来源使用上述隔离业务及访问记录另外证明。

## 取消、确认丢失和恢复

沿用原 TCP 组件事务：审阅身份包括接收策略、全部目标、探测方式及工作程序。写入确认丢失时按原事务核对／恢复，不自动重放修改。取消、验收失败、来源证据失配和远端漂移均按既有组件边界处理。

快照固定保存配置、中转／客户端网段、白名单、systemd 单元和工作程序原始字节；恢复原快照恢复原规则与程序，不覆盖代理协议、Tunnel 或监控。旧快照不被自动升级为可信接收。实例换址同步可信中转地址和相应验收目的地址，仍需新的审阅与验收，不因地址相同就自动信任另一台机器。
